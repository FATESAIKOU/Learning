# LeanCTX 分析報告

## 1. 這個技術解決什麼問題？

AI 編碼代理（Cursor、Claude Code、Copilot 等）在與程式碼互動時存在三個具體問題：

- **重複讀取浪費**：代理每次重新讀取相同檔案消耗約 2,000 tokens，即使檔案內容未變更
- **Shell 輸出噪音**：`git status`、`npm install` 等 CLI 輸出未經篩選直接送入 LLM，裸 `git status` 約消耗 800 tokens
- **跨會話記憶喪失**：每次新聊天啟動時，代理遺忘先前累積的專案理解、已知決策與探索結果，導致 cold start

LeanCTX 將上述三個問題合併為一個統一的 context 管線處理：原始輸入從約 100K tokens 壓縮至約 5K tokens 的有用信號後送入 LLM，同時提供跨會話記憶持久化與適時召回。


## 2. 這個問題為什麼會發生？（背景）

| 面向 | 明確提到（來自 README / ARCHITECTURE.md / VISION.md） | 通用技術背景 |
|---|---|---|
| LLM 計費模型 | AI 編碼代理按 token 計費，每次讀取、每次 shell 命令輸出都消耗 token 預算 | LLM API 普遍採用 per-token 計費（input + output），context window 愈大成本愈高 |
| 代理工具限制 | 現有 AI 編碼代理的原生工具（Read、Grep、Bash）不具備快取、壓縮、跨會話記憶能力 | MCP 協議僅定義工具接口，不規範工具實作的壓縮策略與狀態持久化 |
| Context Window 競爭 | 噪訊（boilerplate、重複內容）擠佔推理空間，降低 LLM 注意力集中度 | Attention 機制對輸入全量計算，無用 tokens 仍消耗計算資源 |
| 跨會話無狀態 | LLM API 多為無狀態設計，不維護跨請求持久記憶。代理每次新聊天從零開始 | 多數 LLM API 不提供服務端會話持久化 |

三個問題的根因可歸結為同一結構性缺陷：AI 編碼代理與 LLM 之間缺少一個專門管理 context 生命週期的中間層。現有架構中，context 是每個請求的臨時產物，而非被治理的持久資源。


## 3. 這個技術是如何解決該問題的？

LeanCTX 是一個用 Rust 寫成的單一二進位，同時作為 **MCP server**（透過 stdio JSON-RPC 提供 68 個工具給 AI 代理調用）和 **shell hook**（以 `~/.zshenv` 攔截終端命令並壓縮輸出）。它不對 LLM 模型本身做任何修改，而是在編碼代理與 LLM 之間插入一個四維度的 context 治理層。

```
AI 工具 (MCP 呼叫 + shell 命令)
        │
        ▼
   lean-ctx binary
   ╔══════════════════════════════════════════════════╗
   ║  Compression  │  Memory  │  Routing  │  Governance  ║
   ╚══════════════════════════════════════════════════╝
        │
        ▼
   送入 LLM 的 context（壓縮後信號 + 召回記憶 + 路由決策）
```

### 3.1 壓縮（Compression）— 降低輸入 token 消耗

| 壓縮對象 | 機制 | 效果 |
|---|---|---|
| 檔案讀取 | 10 種讀取模式：`full`（全文）、`map`（依賴+導出摘要）、`signatures`（AST 簽名）、`diff`（僅變更行）、`aggressive`（最大壓縮）、`entropy`（高資訊密度片段）、`task`（任務相關過濾）、`reference`（最小摘錄）、`lines:N-M`（指定範圍）、`auto`（系統自選） | 快取命中時重複讀取僅 ~13 tokens |
| Shell 輸出 | 56 個模式模組（git、npm、cargo、docker、kubectl、terraform 等，270 條 passthrough 規則） | `git status` 從 ~800 tokens 壓縮至 ~120 tokens |
| AST 結構解析 | Tree-sitter 解析 18 種語言的 AST，提取 class/method/type 簽名而非全文 | 傳送骨架，不傳送實作體 |
| 熵過濾 | Shannon entropy per line，移除資訊量低的行（如連續 import、純 formatting） | 低熵行被排除 |

### 3.2 記憶（Memory）— 跨會話持久化與適時召回

記憶層是 LeanCTX 本質功能之一，不限於壓縮。其核心機制分三層：

**層一：Session 記憶（CCP，Cross-Session Context Protocol）**

```
# AI agent 透過 MCP 寫入 session 記憶
ctx_session action=task    "Refactor auth module [40%]"
ctx_session action=finding "JWT validation in auth/verify.rs L42"
ctx_session action=decision "Use session cookies, not JWT for web UI"
ctx_session action=save    # 快照序列化至 sessions/<id>.json

# 下次開啟新聊天時，LeanCTX 自動偵測同專案
# 從 sessions/latest.json 注入 ~400 tokens 的恢復區塊：
#   Task: Refactor auth module [40%]
#   Findings (20): ...
#   Files (50): [F1 auth.rs map] [F33 schema.rs signatures]
#   Persisted references → 重讀 F1 cost ~13 tokens
```

恢復區塊中的 `[F1]`、`[F33]` 是持久化檔案引用，包含已讀取檔案的壓縮形態，因此新聊天啟動後首次讀取仍然是快取命中（~13 tokens）。

**層二：Knowledge 記憶（專案持久知識庫）**

```
# 寫入事實（可選 category / confidence / key）
ctx_knowledge action=remember content="Payments use Stripe; webhook secret in STRIPE_WH"

# 召回
ctx_knowledge action=recall  query="how do payments work"
ctx_knowledge action=search  query="stripe" mode=hybrid

# 精煉
ctx_knowledge action=consolidate   # 合併重複事實、移除冗餘
ctx_knowledge action=relate        # 建立事實之間的關聯圖

# 生命週期
# max_facts 預設 200，超出時 consolidate 回收空間
# decay → archive → rehydrate 自動維護
# 類別分組合併（O(n) per category）
```

所有記憶操作（recall、search、consolidate）**不呼叫外部 LLM API**。語義搜尋使用本機 ONNX embedding 模型，預設為 all-MiniLM-L6-v2（384 維），透過純 Rust 的 `rten` runtime 在 CPU 上執行。可選切換為 jina-embeddings-v2-base-code（768 維，程式碼優化）或 nomic-embed-text-v1.5（768 維）。

混和搜尋（hybrid）使用 Reciprocal Rank Fusion（RRF）融合三種排名：BM25（詞頻）、dense embedding（語義）、graph proximity（程式碼圖結構距離）。

**層三：Property Graph（程式碼結構圖）**

基於 AST 的多邊圖，邊類型包含 imports、calls、exports、type_ref、tested_by。支援 BFS 多邊遍歷、影響分析、加權搜尋排名。透過 incremental git-diff 更新，不重新解析全專案。

### 3.3 路由（Routing）— 每個讀取操作自動匹配正確精度

- `ModePredictor`：根據歷史 session 記錄學習每個檔案類型的最佳讀取模式（如測試檔案用 `map`、核心邏輯用 `full`）
- `IntentEngine`：分類查詢複雜度（檢索 vs 推理），簡單查詢自動降級為輕量模式
- Adaptive engine：Thompson Sampling bandit 在模式探索與利用間取捨
- Context Gate：pre-dispatch 五道閘（Overlay、Pressure 強制降級、Bounce 預防、Intent-Target 匹配、Graph 距離），post-dispatch 六步後處理（Ledger 記錄、Overlay 檢查、Reinjection、Eviction 提示、Elicitation 提示、Resource 通知）

### 3.4 治理（Governance）— 控制 context window 邊界

- **角色基礎存取控制**：Role Guard 限制每個 role（coder、reviewer、explorer、ops）可調用的 MCP 工具
- **預算與 SLO**：token 上限、shell 呼叫次數上限、成本上限；壓縮率、延遲、快取效率的 SLO 門檻
- **Loop Detection**：重複搜尋節流/阻塞，防止 token 浪費
- **Degradation Policy**：預算耗盡時降級工具行為（如 full → map）
- **Context Proof**：`ctx_proof` 匯出機器可讀的 context 證明（JSON + HTML），`ctx_verify` 檢查 19 版本化合約的 CI drift gates
- **Context Manager**：瀏覽器儀表板（即時 token 使用率、壓縮統計、壓力儀表）


## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式？

LeanCTX 的獨特點是同時覆蓋三個問題域（壓縮、記憶持久化、適時召回），以下替代方案各自僅覆蓋部分：

### DA 表

| 技術名 | 技術解法 | 技術使用前提 | 技術使用副作用 | 技術使用預期效果 |
|---|---|---|---|---|
| **RTK** (rtk-ai/rtk) | 單一讀取模式，基本快取索引 | 依賴雲端服務，需網路 | 無 shell 壓縮、無程式碼圖譜、無跨會話記憶、雲端依賴 | 基本檔案快取與關鍵字搜尋 |
| **Context+** (ForLoopCodes/contextplus) | 基礎過濾規則，對話歷史摘要 | 本機安裝 | 僅對話歷史、無 shell 壓縮、無多代理支援、無 embedding 召回 | 有限的對話上下文過濾 |
| **MemGPT / Letta** | 分層記憶架構（working / episodic / archival），OS 式記憶管理 | 需部署伺服器 | 關注通用對話記憶而非程式碼智慧、無 MCP 工具、無 shell hooks、記憶操作可能觸發 LLM 推論 | 長對話記憶持久化 |
| **手動 Rules 檔案**（CLAUDE.md, .cursorrules, AGENTS.md） | 開發者手寫靜態規則與上下文指引 | 開發者手動撰寫、每專案分別維護 | 無法動態壓縮、無快取機制、僅作用於單一代理、無人為觸發外的召回 | 低維護開銷、無額外依賴，但完全依賴開發者紀律 |

### 切入點差異圖

```
                     壓縮      記憶持久化    適時召回     程式碼理解   治理
RTK                  ●           ○            ○            ○          ○
Context+             ●           ●            ○            ○          ○
MemGPT / Letta       ○           ●            ●            ○          ○
手動 Rules           ○           ●            ○            ○          ○
LeanCTX              ●           ●            ●            ●          ●

● 覆蓋  ○ 不覆蓋
```

RTK 僅處理壓縮。MemGPT/Letta 處理純對話記憶但缺乏程式碼結構理解與 shell 整合。Context+ 在壓縮與記憶之間但不深入。手動 Rules 完全不具自動化。LeanCTX 是唯一在本機單一二進位中覆蓋全部五個面向的技術。

### 與 MemGPT/Letta 的關鍵差異

MemGPT 的記憶召回操作可能觸發 LLM 推論（讓 LLM 決定該從哪層記憶提取什麼）。LeanCTX 的記憶操作（recall、search、consolidate）不呼叫外部 LLM API：語義比對使用本機 ONNX embedding 模型，精煉合併使用規則式去重邏輯。這表示 LeanCTX 的記憶功能自身不消耗 LLM token 預算。
