# Maigret 技術分析報告

> 來源：https://github.com/soxoj/maigret
> 分析日期：2026-06-27

---

## 1. 這個技術解決什麼問題？

**被解決的具體問題**：給定一個「使用者名稱（username）」，缺乏任何其他個人資訊、API 金鑰或登入憑證的前提下，無法在合理時間內跨「數千個網站」自動確認該名稱是否已被註冊為帳號，並把每個找到的帳號所揭露的個人資料（姓名、位置、頭像、外部連結、內部 ID 等）彙整成可供調查的「dossier（檔案）」。

**問題的模糊點**：
- README 標語 `Collect a dossier on a person by username only` 把「username」當成唯一輸入，但實務上同一人多帳號名稱並不一致；Maigret 透過 `--permute` 與 recursive search 緩解，但README 未明確界定「dossier 的最小可信度門檻」。
- 「3000+ sites」的覆蓋率不等於命中率；商業版文件指出開源資料庫需每日維護才不會失效，開源版僅 24 小時自動更新一次。

---

## 2. 這個問題為什麼會發生？（背景）

### 文章中明確提到

| 背景因素 | 內容 |
|---|---|
| 網站數量爆炸 | 支援 3000+ 站點，無法人工逐一檢查 |
| 站點保護機制 | 部分站點啟用 Cloudflare JS Challenge / WAF / CAPTCHA，純 HTTP client 無法通過 |
| 站點結構漂移 | 平台 HTML / API 隨改版變動，解析器需持續維護（商業版強調） |
| 跨服務關聯需求 | 同一人在 GitHub 暴露了 `twitter_username`，需自動 pivot 到 Twitter 查 |
| 暗網 / 鏡像站 | Tor / I2P 站、Picuki 等 Instagram 鏡像需特殊路由與並行處理 |
| 無 API 金鑰前提 | 多數社群平台已關閉公開 API 或需審批，迫使改走 HTML 解析 |

### 通用技術背景（文章未明說，屬 OSINT 領域常識）

```
OSINT username enumeration 的歷史脈絡
├─ 2013~2018：社群平台公開 API 開放，per-site 腳本泛濫
│   └─ 問題：N 個平台 = N 套維護成本，且 API 陸續關閉
├─ 2018：Sherlock 誕生 → 統一 data.json 描述 URL 模板 + status code
│   └─ 只回答「存在 / 不存在」，不抽取內容
├─ 2019：soxoj 分叉 Sherlock → Maigret，引入 socid_extractor
│   └─ 從「探測」升級為「dossier 彙整」
└─ 2024+：平台反爬升級（CF JS challenge、TLS fingerprint）
    └─ Maigret 引入 FlareSolverr / curl_cffi bypass
```

## 3. 這個技術是如何解決該問題的？

### 3.1 系統架構

```
                  ┌────────────────────────────────────────┐
輸入：username ──▶│ Maigret 主流程（asyncio + aiohttp）    │
                  │                                        │
                  │  1. 載入 sites database (data.json)    │
                  │     └─ 每 24h 從 GitHub auto-update     │
                  │  2. 依 tags / 排名挑選子集             │
                  │  3. 對每個 site 並行發 HTTP request     │
                  │     ├─ 一般站：aiohttp / curl_cffi      │
                  │     ├─ CF 保護站：FlareSolverr webgate  │
                  │     └─ Tor/I2P：proxy chain             │
                  │  4. 套用 site 專屬 detection rule       │
                  │     └─ checkType: status_code /         │
                  │        response_url / message           │
                  │  5. socid_extractor 解析回應            │
                  │     └─ 抽 uid / fullname / links / ...  │
                  │  6. recursive search：                  │
                  │     └─ 從 links 中找出新 username → 回 1│
                  │  7. 彙整 report（HTML/PDF/XMind/JSON）  │
                  └────────────────┬───────────────────────┘
                                   │
                   可選：--ai 送到 OpenAI-compatible endpoint
                                   │
                                   ▼
                          investigation summary
```

### 3.2 sites database（核心資產）

每筆 site 條目包含：

```json
{
  "GitHub": {
    "url": "https://github.com/{username}",
    "urlMain": "https://github.com",
    "usernameClaimed": "blue",
    "usernameUnclaimed": "noonewouldeverusethis7",
    "checkType": "status_code",
    "tags": ["coding", "us"],
    "protection": [],
    "activation": null
  }
}
```

- `usernameClaimed` / `usernameUnclaimed`：用於 `--self-check` 驗證 detection rule 是否仍然有效
- `protection`：標記 `cf_js_challenge` / `cf_firewall`，決定是否走 Cloudflare bypass
- `checkType`：決定如何判斷帳號存在
  - `status_code`：比對 HTTP status
  - `response_url`：比對最終 URL（防 redirect 到登入頁）
  - `message`：在回應內容中找特定字串

### 3.3 三層偵測機制

| 層級 | 做什麼 | 由誰負責 |
|---|---|---|
| L1 帳號存在性 | 判定 yes/no | Maigret detection rule |
| L2 結構化欄位抽取 | 抽 130+ 站的 30+ 欄位 | socid_extractor |
| L3 跨服務 pivot | 從 `links` / `twitter_username` 等欄位找到新 ID，遞迴回到 L1 | Maigret recursive search |

### 3.4 反封鎖機制

| 機制 | 觸發條件 | 做法 |
|---|---|---|
| Cloudflare webgate | `protection` 含 `cf_js_challenge` | 轉發至本地 FlareSolverr（真 Chrome 解 JS challenge），session 重用加速 5–10× |
| Activation | 站點需 cookie/JWT | 自訂函式先打認證 endpoint，更新 DB 中該站的 headers/cookies，再重試 |
| Proxy / Tor / I2P | 使用者指定 | aiohttp 串 SOCKS5 / HTTP proxy |
| Censorship 偵測 | 同類錯誤 > 3% | CLI 警告 + 建議 |
| Retries | 暫時性錯誤 | 預設 1 次，`--retries N` 可調 |
| 鏡像 fallback | 主站被擋 | DB 內含 Picuki 等 mirror 條目 |

### 3.5 AI 分析模式

```
search results ──▶ 內部 Markdown report ──▶ OpenAI-compatible chat
                                                │
                                                ▼
              固定格式 summary：likely real name / location / occupation /
              interests / languages / main website / username variants /
              platforms count / active years / confidence / follow-up leads
```

- 任何 OpenAI 相容 endpoint 皆可（Azure、OpenRouter、本地 server）
- `--ai` 時抑制 per-site 進度，僅 stream summary

### 3.6 使用方式（虛擬碼）

```bash
# 基本查詢（預設 top 500 站）
maigret USERNAME

# 全站 + 遞迴 + AI 摘要
maigret USERNAME -a --ai

# 從一個已知 profile URL 反解
maigret --parse https://github.com/soxoj

# 帳號名稱排列組合
maigret --permute john doe   # 產生 johndoe / john_doe / ... 共 12 種

# 自我驗證資料庫
maigret --self-check --auto-disable
```

## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式？

### 4.1 同類技術 DA 表

| 技術名 | 技術解法 | 技術使用前提 | 技術使用副作用 | 技術使用預期效果 |
|---|---|---|---|---|
| **Sherlock** | 統一 `data.json` 描述 URL 模板 + status code 比對，只回傳存在/不存在 | Python 3.x；無需 API key | 不抽取個人資料；無遞迴；無 CF bypass | 跨 400+ 站快速列點命中清單 |
| **WhatsMyName** | 與 Sherlock 同類，`web_accounts_list.json` 維護偵測規則，提供 JSON/UI 呈現 | Python / Web UI | 不做 dossier 彙整；站點數較少（~600） | 輕量列點 + 較嚴謹的 false positive 控制 |
| **Maltego** | 圖形化 transform graph，手動/半自動 pivot；以「entity → transform」圖論思維擴展 | Java；商業授權（Community 版受限）；需手動安裝 transforms | 學習曲線陡；transforms 需逐一設定 | 視覺化關聯圖、可串接付費資料來源 |
| **SpiderFoot** | 自動化 OSINT 编排引擎，200+ modules 跨多種 input（email/IP/domain/username） | Python；可選 H2 database | 模組品質不一；大量請求易觸發封鎖 | 以「target 為中心」的全自動 footprint，輸出圖表與 report |

### 4.2 切入點差異

```
              輸入單純度
                  ▲
                  │
  Maigret ●       │       ● Sherlock
  (username only) │   (username only, 無抽取)
                  │
                  │       ● WhatsMyName
                  │   (username only, 輕量)
                  │
                  │       ● SpiderFoot
                  │   (多輸入, 全自動 footprint)
                  │
                  │       ● Maltego
                  │   (多輸入, 手動 pivot, 圖論)
                  ▼
              輸出豐富度 ──────────▶
```

- **Sherlock / WhatsMyName**：以「探測」為終點，不進入 L2 抽取、不進入 L3 遞迴
- **Maigret**：在 L1 之上疊加 socid_extractor（L2）與 recursive pivot（L3），把「探測器」升級為「dossier 產生器」
- **SpiderFoot**：輸入维度更廣（不限 username），但 module 品質離散
- **Maltego**：圖論思維，適合手動調查與付費資料源整合，不適合無人值守批次

### 4.3 Maigret 在光譜中的定位

| 維度 | Maigret | 同類相對位置 |
|---|---|---|
| 輸入要求 | 僅 username | 最低（與 Sherlock 同級） |
| 站點覆蓋 | 3000+ | 最高（開源） |
| 內容抽取 | 130+ 站、30+ 欄位 | 高於 Sherlock，低於 Maltego+付費 source |
| 自動 pivot | 預設啟用遞迴 | 同類開源中獨有 |
| 反封鎖 | FlareSolverr + activation + proxy | 同類開源中最完整 |
| AI 摘要 | 內建 `--ai` | 同類開源中獨有 |

## 5. User Q&A

### Q1：Maigret 到底是在解決「誰」的「什麼」問題？

**A**：Maigret 的使用者與被解決的問題可拆為三層。

#### 一、「誰」在用——使用者光譜

| 使用者類型 | 為什麼需要 Maigret | 真實範例 |
|---|---|---|
| **OSINT 調查員 / 記者** | 接到線索只有一個帳號名稱（如爆料帳號、受害者提供的嫌犯 ID），需快速確認此人在哪些平台活動 | Bellingcat 調查團隊以 username 為起點重建嫌疑人足跡 |
| **資安 / 紅隊人員** | 滲透測試前期的 recon 階段，從目標員工的公開帳號收集可利用資訊（email、生日、興趣、社交連結） | Pentest engagement 中以目標公司員工 username 起手 |
| **執法 / 反詐騙單位** | 詐騙帳號、失蹤人口、網路犯罪者追蹤，只有帳號名稱可資 | 反詐專案小組從一個 Telegram 帳號名 pivot 到其他平台 |
| **一般使用者（自助隱私審計）** | 想知道「我自己用的這個 ID，在網路上到底洩漏了多少足跡」 | 個人輸入自己的常用 username 自查 |
| **商業 OSINT 平台（下游整合者）** | 把 Maigret 當引擎嵌入自家產品，省去自行維護 3000+ 站規則 | Social Links API、UserSearch（README 明列為 Used by） |

#### 二、「什麼」問題——被解決的具體痛點

```
痛點拆解（以一名 OSINT 調查員的實際工作流程為例）

  手上線索：一個 username「soxoj」

  ┌─ 痛點 1：站點太多，人工不可能
  │   要查的平台 = 3000+
  │   一人手動開 3000 個分頁逐頁搜尋 → 物理上不可行
  │
  ├─ 痛點 2：每個平台的「帳號是否存在」判定邏輯不同
  │   GitHub：404 = 不存在
  │   Instagram：redirect 到登入頁 = 不存在
  │   某論壇：頁面內容含「User not found」字串 = 不存在
  │   → 需要一個「per-site detection rule 資料庫」統一描述
  │
  ├─ 痛點 3：找到帳號只是起點，還要抽出可調查的資料
  │   帳號頁面上的 fullname / location / email / 頭像 / 外部連結
  │   都是下一步 pivot 的素材，但每個平台 HTML 結構不同
  │   → 需要 per-site parser（socid_extractor 負責）
  │
  ├─ 痛點 4：同一人在不同平台用不同 username
  │   GitHub 上的 bio 寫了 twitter_username = "sox0j"
  │   調查員不會手動看到這行再去查 sox0j
  │   → 需要自動 recursive pivot
  │
  ├─ 痛點 5：平台越來越會擋機器人
  │   Cloudflare JS Challenge / WAF / CAPTCHA
  │   純 aiohttp 發 request 會被擋回 403
  │   → 需要 bypass 機制（FlareSolverr）
  │
  └─ 痛點 6：結果要能交差
      調查產出需整理成可閱讀、可移交的 dossier
      → 需要 HTML / PDF / XMind / graph 多格式 report
```

#### 三、一句話收斂

| 問題層級 | 一句話描述 |
|---|---|
| 表層問題 | 給一個 username，跨 3000+ 站快速判定帳號是否存在 |
| 中層問題 | 找到帳號後，自動抽出個人資料並 pivot 到其他帳號 |
| 核心問題 | 把「只有一個帳號名稱」這個極薄弱的起點，自動擴張成一份可調查、可移交的人物檔案 |

**結論**：Maigret 服務的是「以 username 為唯一線索起點的 OSINT 調查工作流」，解決的是「人工跨站調查在站點數量、判定邏輯、資料抽取、跨帳號 pivot、反封鎖、產出格式」六個環節的不可行性」。

### Q2：這個問題的發生背景是什麼？為什麼會演變到需要 Maigret 這種工具？

**A**：背景可從「需求側」與「供給側」兩條線索拆解。

#### 一、需求側——OSINT 為何興起、為何以 username 為常見起點

| 時間 | 事件 | 對 OSINT 需求的影響 |
|---|---|---|
| 1941 | 美國成立 FBMS（外國廣播監聽） | OSINT 概念萌芽，但以廣播/報紙為源 |
| 2001 | 9/11 事件 | 情報界反思「公開來源被嚴重低估」，9/11 委員會建議設立 OSINT 專責機構 |
| 2004~2005 | 美國設立 Open Source Center（DNI） | OSINT 正式制度化 |
| 2010s | 社群平台爆炸（FB/Twitter/IG/TikTok/Reddit） | 人類大量活動遷移到網路公開頁，OSINT 來源從媒體轉為社群個資 |
| 2014~ | Bellingcat 以 OSINT 調查馬航 MH17、敘利亞戰爭 | OSINT 從情報圈擴散到記者、公民調查者 |
| 2020s | 詐騙、網路釣魚、深度偽造普及 | 執法、資安、一般使用者都需要以「帳號」為線索反向追人 |

**為何 username 是常見起點**：實務上調查者最常拿到的線索強度排序：

```
線索強度（由強到弱）
├─ Email / 電話 → 可直接反查洩漏庫、社交帳號
├─ 真實姓名 → 可查公開記錄、新聞
├─ 帳號名稱（username） → 只能逐站試探  ← Maigret 切入點
├─ IP / device fingerprint → 需技術手段
└─ 行為側寫 → 需大量樣本
```

username 是「最常拿到、但最難單獨利用」的線索——它在詐騙對話、論壇貼文、截圖中隨處可見，但單憑一個名稱無法直接反查。這個落差就是 Maigret 補的缺口。

#### 二、供給側——為什麼不能直接用各平台官方 API

| 限制類型 | 具體情況 | 對工具設計的影響 |
|---|---|---|
| API 關閉 | Instagram、Twitter/X 先後關閉免鑑權公開 API（2018~2023） | 必須改走 HTML 解析 |
| API 審批 | Facebook Graph API、TikTok API 需申請 + 商業審核 | 開源工具無法取得，被迫走 scraping |
| Rate limit | 即使有 API 也嚴格限流 | 需支援 proxy / Tor / retry |
| 反爬升級 | Cloudflare JS Challenge、TLS fingerprint 偵測 | 需 FlareSolverr、curl_cffi 等 bypass |
| 站點結構漂移 | 平台改版導致 HTML / API endpoint 變動 | 需可持續維護的 detection rule 資料庫 |
| 暗網鏡像 | 部分站點被牆或需 Tor | 需支援 .onion / .i2p 路由 |

#### 三、工具演進時間線——Maigret 為何在此時出現

```
2013 ─ 社群平台公開 API 還算寬鬆
│      → 每個平台各自有 scrapers，散亂維護
│
2018 ─ Sherlock 誕生
│      → 統一 data.json 描述 URL 模板 + status code
│      → 解決「站點太多、判定邏輯分散」的痛點 1、2
│      → 但只到「帳號是否存在」，不抽取、不 pivot
│
2019 ─ soxoj fork Sherlock → Maigret
│      → 疊加 socid_extractor（解決痛點 3）
│      → 疊加 recursive search（解決痛點 4）
│      → 引入 tags、鏡像站、self-check
│
2023 ─ 平台反爬全面升級
│      → Maigret 引入 FlareSolverr webgate（解決痛點 5）
│      → 引入 activation mechanism
│
2024 ─ LLM 成熟
│      → Maigret 加 --ai，把 raw findings 轉成可讀 summary
│      → 解決痛點 6 的「可交差」需求
```

#### 四、背景對照表——文章明說 vs. 通用背景

| 背景因素 | 來源 | Maigret 如何回應 |
|---|---|---|
| 3000+ 站點 | README 明列 | 統一 sites database + 24h auto-update |
| 平台 API 關閉/審批 | 通用背景（README 僅說 No API keys required） | 走 HTML 解析 + socid_extractor |
| Cloudflare / WAF 升級 | README features 頁明列 | FlareSolverr webgate bypass |
| 站點結構漂移 | 商業版段落明列「site checks break over time」 | self-check + auto-disable + 商業版每日維護 |
| 跨帳號 pivot 需求 | README features 頁明列 recursive search | 預設啟用，從 links / ids 自動遞迴 |
| 暗網 / 鏡像 | README 明列 Tor/I2P/Picuki | proxy chain + DB 內含鏡像條目 |
| OSINT 制度化需求 | 通用背景（Wikipedia OSINT 條目） | Maigret 不解決制度化，僅提供工具層 |
| 以 username 為最弱線索 | 通用背景（SOWEL SOTL-2.2 / 6.2） | Maigret 把弱線索自動擴張為 dossier |

**結論**：Maigret 出現的背景是「OSINT 需求從情報圈普及到記者/資安/執法/一般人」+「社群平台 API 逐漸關閉且反爬升級」+「既有工具（Sherlock）只解決探測、不解決抽取與 pivot」三條線交會的產物。
