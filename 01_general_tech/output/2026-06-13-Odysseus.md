# Odysseus — 技術分析報告

## 1. 這個技術解決什麼問題？

**被解決的具體問題：** 使用者需要一個可在自有硬體上運行的、整合了 LLM 聊天、AI Agent 工具執行、本地模型下載與伺服、深度研究、文件編輯、郵件/行事曆/筆記管理的「一站式 AI 工作空間」，且所有資料留在本地、不依賴第三方雲端服務。

**模糊之處：** README 自述為「ChatGPT / Claude 的 self-hosted 版 UI 體驗」，但未明確定義其目標使用者規模（單人 vs 團隊）、也未說明與 opencode（其 Agent 底層）的責任邊界。

---

## 2. 這個問題為什麼會發生？（背景）

### 文章中明確提到的背景

- 現有 AI 聊天產品（ChatGPT、Claude）的資料與運算都在雲端，使用者無法控制資料流向與模型選擇。
- 本地模型服務（Ollama、vLLM、llama.cpp）各自獨立，缺乏統一的 UI 層來管理下載、伺服、切換模型。
- Agent 工具呼叫（shell、檔案讀寫、網頁搜尋、MCP）需要一個安全的執行環境與權限模型。
- 郵件、行事曆、筆記等生產力工具分散在不同應用中，缺乏 AI 代理的統一接入點。

### 通用技術背景（文章中未明確提及，但構成問題脈絡）

- 開源 LLM 生態在 2024–2025 年爆發式成長（Llama、Qwen、DeepSeek 等），但「下載→量化→伺服→使用」的流程對非技術使用者仍有門檻。
- MCP（Model Context Protocol）於 2024 年底由 Anthropic 提出，作為 LLM 與外部工具間的標準協議，但多數 self-hosted UI 尚未深度整合。
- Self-hosted AI UI 領域已有 Open WebUI、LibreChat、AnythingLLM 等競品，但多數聚焦於聊天，缺乏 Agent 迴圈、深度研究、郵件/行事曆整合。

---

### 3.1 Agent 迴圈（基於 opencode 模式）

Agent 迴圈的核心在 `src/agent_loop.py`（187KB），採用 **fenced code block** 工具呼叫模式：

```
使用者輸入 → LLM 串流回應 → 正則解析 ```tool_name ... ``` 區塊
    → 執行工具 → 結果注入對話 → LLM 繼續 → 直到 LLM 宣告 DONE/BLOCKED
```

**工具呼叫格式：**
```bash
```bash
#!bg
pip install openai-whisper
```
```

```web_search
{"query": "latest AI news", "time_filter": "day"}
```

**關鍵設計決策：**
- 工具以 **denylist** 控管（`tool_security.py:NON_ADMIN_BLOCKED_TOOLS`），非 admin 使用者無法執行 shell/python/檔案讀寫/郵件/行事曆/MCP 等 40+ 工具
- **Plan mode**：以 allowlist 反向操作（`PLAN_MODE_READONLY_TOOLS`），只允許唯讀工具，任何新增工具預設被封鎖（fail safe）
- **Domain-based tool rules**：根據可用工具集合動態注入對應的領域規則（web/documents/email/cookbook/notes_calendar_tasks/ui/sessions/files/settings），避免 prompt 膨脹
- **Internal tool loopback**：Agent 工具呼叫透過 in-process HTTP loopback 到達 admin-gated 路由，使用 `secrets.token_hex(32)` 隨機 token 驗證，token 不持久化、不傳送給客戶端
- **Context compaction**：當上下文使用率達 85% 時，自動將前半對話摘要為結構化 summary（`context_compactor.py`），保留後半對話；支援 tool_calls/tool 訊息配對修復

### 3.2 MCP 整合

`src/mcp_manager.py` 實作三種傳輸層：

| 傳輸 | 用途 | 驗證 |
|------|------|------|
| **stdio** | 本地子行程 MCP 伺服器 | 無（本地信任） |
| **SSE** | 遠端 Server-Sent Events | URL 連接 |
| **Streamable HTTP** | 遠端 HTTP + OAuth | `mcp_oauth.py` 實作 DCR + 瀏覽器授權流程 |

**安全措施：**
- MCP 工具名稱以 `mcp__{server_id}__{tool_name}` 命名空間隔離
- 工具 schema 參數渲染時做 sanitize（`_MCP_PARAM_MAX=12`, `_MCP_TOKEN_MAX=40`, `_MCP_HINT_MAX=300`），防止惡意 schema 污染 prompt
- Plan mode 下所有非唯讀 MCP 工具被封鎖（`mcp_tool_is_readonly()` 先看 annotations，再看動詞啟發式，fail closed）
- 非 admin 使用者所有 `mcp__*` 工具被封鎖
- Builtin MCP 伺服器崩潰時自動重連（`_reconnect_builtin()`）

### 3.3 Cookbook（本地模型伺服）

- 基於 **llmfit** 做硬體掃描（VRAM、RAM、GPU 型號）
- 支援 GGUF / FP8 / AWQ 量化格式
- 透過 **tmux** 管理背景模型下載與伺服（vLLM / llama.cpp / SGLang）
- 遠端伺服器支援：SSH key 管理，`serve_model` 透過 SSH 在遠端主機啟動 tmux session 並註冊到 `cookbook_state.json`
- Docker 內 GPU passthrough 診斷腳本（NVIDIA/AMD）
- macOS 使用 llama.cpp/Ollama 走 Metal；vLLM/SGLang 僅限 CUDA/ROCm

### 3.4 Deep Research（深度研究）

`src/deep_research.py` 實作 **IterResearch** 模式（改編自 Alibaba Tongyi DeepResearch）：

```
Planning → Think(生成查詢) → Search(多提供者並行) → Extract(LLM萃取)
    → Synthesize(更新報告) → Decide(LLM判斷是否停止) → Final Report
```

- 支援 SearXNG / Brave / Tavily 等多搜尋提供者，含 fallback chain
- 自動分類問題類型（product/comparison/howto/factcheck），套用對應報告模板
- 萃取並行度受 `Semaphore` 控管，避免淹沒本地模型伺服器
- 最終報告自動擴展（若 <400 字則要求 LLM 擴寫）
- 合成失敗時有 fallback report（直接列出所有 findings）

### 3.5 安全模型

| 層級 | 機制 |
|------|------|
| **認證** | bcrypt 密碼 + TOTP 2FA + 8 個一次性備用碼 + 7 天 session token |
| **授權** | Admin / Non-admin 角色分離；40+ 工具對 non-admin 封鎖；admin-only routes 由 `require_admin` middleware 控管 |
| **提示注入防護** | `UNTRUSTED_CONTEXT_POLICY` 系統提示 + `untrusted_context_message()` 以 `<<>>` guard markers 包裹外部內容，並 escape 內部出現的 marker 字面值 |
| **Internal loopback** | `secrets.token_hex(32)` 隨機 token，不持久化，僅在 process 內傳遞 |
| **Security headers** | CSP (nonce-based script-src), X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer |
| **Session 安全** | 保留使用者名稱 (`internal-tool`, `api`, `demo`, `system` 禁止註冊)；orphan session 自動失效 |
| **CI 安全** | gitleaks (secret scan), actionlint+zizmor (workflow), dependency-review, pip-audit, hadolint, Trivy, CodeQL |

**已知安全缺口（文件中明確列出）：**
1. 無 shell/filesystem sandbox（Agent bash 以 app process 使用者身分執行，無網路 egress 過濾或檔案系統 confinement）
2. SSRF via `/api/v1/chat` `base_url` parameter（PR #1039 修復中）
3. `src/search/` 部分模組與 `services/search` 程式碼重複，可能 drift
4. Token scopes 粗糙（僅 `chat` / `admin`，無 per-capability 粒度）

## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式？

### DA 表（Decision Analysis）

| 技術名 | 技術解法 | 技術使用前提 | 技術使用副作用 | 技術使用預期效果 |
|--------|----------|-------------|---------------|-----------------|
| **Open WebUI** | Python/FastAPI + Svelte 前端；Ollama/OpenAI API 整合；管線(Pipelines)插件系統 | 需 Ollama 或 OpenAI-compatible API；Docker 或 Python venv | 無內建 Agent 迴圈（需依賴外部工具如 opencode）；無深度研究引擎；無郵件/行事曆整合；權限模型較簡單 | 提供 Ollama 生態最完整的 Web UI，適合已使用 Ollama 的使用者 |
| **LibreChat** | Node.js/Express + React；多模型 API 整合；支援檔案上傳、程式碼解釋 | 需 Node.js 環境；API key 設定 | 無本地模型下載/伺服功能；無 Agent 工具執行迴圈；無 MCP 整合；無深度研究 | 提供接近 ChatGPT 的多模型聊天體驗，適合偏好 Node.js 生態者 |
| **AnythingLLM** | Node.js/Express + React；RAG 文件問答；多模型 API；workspace 隔離 | 需 Node.js；Docker 或 npm | 聚焦於文件 RAG 而非通用 Agent；無 Cookbook 式模型管理；無郵件/行事曆；Agent 能力有限 | 適合以文件問答為主要場景的團隊使用 |
| **Msty** | Electron 桌面應用；本地模型 + API；離線優先 | 需安裝桌面應用 | 非 self-hosted Web UI（單機桌面應用）；無多人使用；無 MCP；無深度研究 | 適合個人單機使用、偏好桌面應用體驗者 |

### 各技術解決問題的切入點差異

- **Open WebUI**：從 Ollama 生態切入，聚焦於模型管線與插件擴展，適合已有 Ollama 基礎設施的使用者。
- **LibreChat**：從「多模型 API 聚合聊天」切入，模擬 ChatGPT/Claude 的對話體驗，不涉及本地模型管理。
- **AnythingLLM**：從「RAG 文件問答」切入，以 workspace 為組織單位，適合企業知識庫場景。
- **Msty**：從「桌面應用」切入，強調離線與隱私，不提供 Web 多人存取。
- **Odysseus**：從「all-in-one AI workspace」切入，將聊天、Agent、模型管理、深度研究、郵件、行事曆、筆記整合在單一 self-hosted 應用中，並以 opencode Agent 迴圈為核心差異化能力。
