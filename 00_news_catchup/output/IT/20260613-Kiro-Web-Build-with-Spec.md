# 07. Kiro Web の Build with Spec で Spec 作成から PR・レビュー対応まで試してみた

**Source**: https://dev.classmethod.jp/articles/kiro-web-build-with-spec-workflow/
**Author**: cm-suzuki-ryo (Classmethod)
**Date**: 2026-06-13
**Category**: 傳統IT技術

## 1. この技術/政策は何を解決するのか?

Kiro Web の Build with Spec は、**AI 駆動開発における「仕様の曖昧さ」と「実裝の斷片化」の二重課題**を解決する。

| 課題 | 従來の AI コーディングの問題 | Build with Spec の解決策 |
|------|---------------------------|------------------------|
| 仕様の暗黙性 | プロンプトだけでコード生成すると、設計意図が失われる | Requirements → Design → Tasks の構造化された仕様を自動生成 |
| 実裝の斷片化 | 単発のコード生成ではファイル間の整合性が保証されない | 16 タスクを Wave 0〜5 の依存順序で実行し、全ファイルを一貫生成 |
| レビュー対応の手間 | 人間がコード修正して再コミットする必要がある | `/kiro fix` でレビュー指摘を自動反映し、新しいセッションで修正 |
| 環境セットアップの障壁 | IDE 拡張（VS Code）のインストールと設定が必要 | ブラウザのみで完結。ローカル環境不要 |
| 仕様と実裝の乖離 | 仕様書とコードが獨立に管理され、同期が崩れる | Spec がコード生成の直接入力であり、トレーサビリティが保証される |

検証記事では、VPC Flow Logs（version 11）の CloudWatch Logs Insights クエリチートシート作成という具體的タスクで、Spec 作成から PR 作成、レビュー指摘の自動修正までを 4 分 14 秒で完結させている。

## 2. この問題が発生する背景は?

**AI コーディングアシスタントの現狀と限界**：

2026 年時點で、Cursor, GitHub Copilot, Claude Code などの AI コーディングツールは広く普及しているが、以下の構造的限界が顕在化している：

1. **プロンプトのみの開発は「仕様の揮発性」を生む**：開発者が「〇〇を作って」と指示すると、AI はコードを生成する。しかし、そのコードが「どのような要件に基づき、どのような設計判斷を経て、どのようなタスク分割で実裝されたか」は、プロンプト履歴の中にしか存在しない。1 週間後に修正が必要になった時、その文脈は失われている。

2. **マルチファイル生成の整合性問題**：単一ファイルの生成は得意だが、5 ファイル・940 行に及ぶ変更を一貫して行うには、ファイル間の依存関係（インポート、インターフェース、設定ファイルとの整合）を管理する必要がある。従來の AI ツールはこの「クロスファイル整合性」を作業者の手動確認に委ねていた。

3. **レビュー→修正のループが自動化されていない**：PR レビューで指摘を受けた後、開発者は再度 AI に修正を指示するか、手動で修正する必要があった。この「レビュー指摘の理解 → 修正箇所の特定 → 修正の実裝 → 再コミット」というループは、AI がコードを書く速度に対してボトルネックとなっていた。

4. **IDE 依存の障壁**：VS Code 拡張として提供される AI ツールは、VS Code を使用しない開発者（JetBrains ユーザー、端末ベースの開発者）や、一時的な貢獻者（OSS に初めて PR を送る人）にとって參入障壁となる。

**Spec 駆動開発の思想的背景**：

Build with Spec のアプローチは、以下の開発方法論の系譜に位置づけられる：

- **Design Doc 文化**（Google）：コードを書く前に設計文書を書き、レビューを受ける。AI がこの設計文書作成を自動化する
- **RFC プロセス**（Rust, Python）：言語やフレームワークの変更は RFC として提案・議論される。Spec はプロジェクトレベルの RFC に相當
- **BDD/TDD**：振る舞いやテストを先に定義し、コードはそれを満たすように書く。Spec は BDD の「振る舞い定義」を AI が生成する形

## 3. この技術/政策はどのようにその問題を解決するのか?

**Build with Spec のワークフロー詳細**：

```
[開発者]                    [Kiro Web]
   |                            |
   |-- プロンプト入力 ---------->|
   |   "VPC Flow Logs v11 の     |
   |    チートシートを作成"       |
   |                            |-- Clarifying Questions 生成
   |<-- 4つの確認質問 ----------|   (言語、スコープ、構成、配置)
   |                            |
   |-- 回答選択 --------------->|
   |   "日本語" "新フィールド"   |
   |   "ユースケース別" "ルート" |
   |                            |-- Quick Plan 生成
   |                            |   Requirements: 8要件
   |                            |   Design: 7コンポーネント
   |                            |   Tasks: 16タスク (Wave 0-5)
   |                            |
   |-- フィードバック --------->|
   |   "NAT Gateway のフィルタ値 |
   |    を修正"                  |
   |                            |-- Spec 修正反映
   |                            |
   |-- 承認 ------------------->|
   |                            |-- タスク実行 (4分14秒)
   |                            |   Wave 0 → Wave 1 → ... → Wave 5
   |                            |   5ファイル, 940行生成
   |                            |
   |-- PR作成指示 ------------->|
   |                            |-- ブランチ作成 + push + PR #6
   |                            |
   |-- レビューコメント投稿 ---->|
   |   (3点の指摘)               |
   |                            |
   |-- /kiro fix 投稿 --------->|
   |                            |-- 新セッション自動起動
   |                            |-- 3点の指摘を認識
   |                            |-- 修正実裝 + コミット
```

**Clarifying Questions の戦略的意義**：

Kiro がプロンプト入力後に 4 つの確認質問を提示するフェーズは、AI 駆動開発における最も重要な発明の一つである。従來の AI コーディングでは、プロンプトの曖昧さがそのままコードの曖昧さに転寫されていた。Clarifying Questions は、以下の効果を持つ：

- **暗黙の前提を可視化**：「日本語で書く」という前提は開発者の頭の中にしかなかったが、質問によって明示化される
- **スコープの境界を設定**：「新フィールド活用を中心に」という制約が、AI が無関係なクエリを生成することを防ぐ
- **出力形式の期待値を一致させる**：「ユースケース別構成」「ルートに獨立ファイル」という具體的な指示が、生成結果の手戻りを防ぐ

**Wave 実行の依存管理**：

16 タスクを Wave 0〜5 に分割する設計は、タスク間の依存関係を管理するための仕組みである：

```
Wave 0: 前提タスク（フィールドリファレンステーブルの作成など）
Wave 1: Wave 0 の成果物に依存するタスク
Wave 2: Wave 1 の成果物に依存するタスク
...
Wave 5: 最終的な統合・整形タスク
```

この分割により、ある Wave のタスクが失敗しても、依存する後続 Wave には影響が波及しない。また、各 Wave の完了時に中間成果物がコミットされるため、問題が発生した場合のロールバックが容易である。

**`/kiro fix` の自動修正メカニズム**：

`/kiro fix` は PR レビューコメントを入力として、以下の処理を行う：

1. レビューコメントの自然言語解析（3 點の指摘を獨立に認識）
2. 各指摘に対応するソースコード箇所の特定
3. 修正の実裝（フィールドリファレンステーブルへの `az-id` 追加、パーセントエンコード注記の追加、`!= "-"` 條件の検討）
4. 修正內容のコミットと PR へのプッシュ

このプロセスは、人間の開発者が行う「レビュー指摘の理解 → コード修正 → コミット」というループを、AI が自律的に完結させるものである。

## 4. 類似の問題を解決する他の技術/フレームワーク/考え方は存在するか?

**AI 駆動開発ワークフローの比較**：

| ツール/アプローチ | Spec 生成 | マルチファイル整合性 | レビュー自動修正 | 環境 | 成熟度 |
|-----------------|----------|-------------------|----------------|------|--------|
| Kiro Web Build with Spec | ○（構造化 Spec） | ○（Wave 実行） | ○（/kiro fix） | ブラウザ | 公開プレビュー |
| Cursor + Rules for AI | △（.cursorrules で指示） | △（Composer で複數ファイル） | ×（手動） | IDE | GA |
| GitHub Copilot Workspace | ○（Plan → Code） | ○（マルチファイル） | △（提案のみ） | ブラウザ | プレビュー |
| Claude Code + CLAUDE.md | △（CLAUDE.md で指示） | ○（セッション內で複數ファイル） | △（手動指示） | CLI | GA |
| Amazon Q Developer | △（/dev コマンド） | △（ファイル単位） | × | IDE/CLI | GA |
| Windsurf (Codeium) | △（Cascade で対話的） | △（マルチファイル対応） | × | IDE | GA |

**Spec 駆動開発の代替アプローチ**：

| アプローチ | 具體的手段 | Kiro との比較 |
|-----------|-----------|------------|
| 人間が Spec を書き AI が実裝 | 開発者が要件・設計を Markdown で書き、AI に実裝指示 | Spec の品質は人間のスキルに依存。Kiro は Spec 生成も自動化 |
| TDD + AI | 人間がテストを書き、AI がテストを通すコードを生成 | テストが Spec の役割を果たす。ただしテスト作成コストが高い |
| ドメイン特化 DSL | PDL（Prompt Declaration Language）など | 學習コストが高い。汎用性に欠ける |
| 対話的リファインメント | AI と対話しながら徐々に仕様を明確化 | 仕様がセッション內に留まり、再利用・共有が困難 |

**Kiro Web の獨自的価値**：

Kiro Web の Build with Spec が他の AI コーディングツールと最も異なる點は、**Spec を「生成物」ではなく「開発プロセスの中心的な資産」として位置づけている**ことである。Spec はコード生成の入力であると同時に、プロジェクトのドキュメントとして殘り、將來の修正や他者への引き継ぎの基盤となる。

このアプローチは、AI がコードを書く速度が人間を超えた時代において、「速く書くこと」よりも「正しく書くこと」「保守可能な狀態で書くこと」に価値がシフトしていることを反映している。

また、ブラウザ完結という選択は、オンボーディングコストの最小化という明確な戦略に基づく。OSS 貢獻者や一時的なプロジェクト參加者が、IDE のセットアップなしに貢獻できることは、コミュニティの拡大に直結する。
