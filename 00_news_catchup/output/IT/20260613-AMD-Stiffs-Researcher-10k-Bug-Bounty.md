# 05. AMD Stiffs Researcher $10k Bug Bounty

**Source**: https://www.gadgetreview.com/amd-stiffs-researcher-10000-bug-bounty-after-critical-security-flaw-takes-124-days-to-fix
**Author**: Al Landes
**Date**: 2026-06-13
**Category**: 傳統IT技術

## 1. この技術/政策は何を解決するのか?

このインシデントが暴露した本質的課題は、**ソフトウェアアップデートの配信経路における完全性検証の欠如**である。AMD の Windows 向け自動アップデータ（Ryzen Master およびその他ユーティリティ）は、アップデートファイルを暗號化されていない HTTP 接続でダウンロードしていた。これは以下の具體的リスクを生む：

| リスク | 攻撃シナリオ |
|--------|------------|
| リモートコード実行（RCE） | 中間者攻撃（MITM）により正規のドライバ/ソフトウェア更新をマルウェアに置換 |
| サプライチェーン汚染 | ネットワーク経路上の任意のノードが更新パッケージを改竄可能 |
| 検証不能な修正 | 修正後も CRC32 のみで検証し、暗號署名を実裝せず |

この問題は AMD だけのものではない。ソフトウェアアップデータのセキュリティは、OS レベル（Windows Update, apt, yum）では TLS と GPG 署名によって保護されているが、サードパーティ製ハードウェアユーティリティのアップデータは、往々にしてセキュリティ設計が不十分である。

## 2. この問題が発生する背景は?

**技術的背景：なぜ HTTP が使われていたのか**

AMD の自動アップデータが HTTP を使用していた理由は、以下の構造的要因に遡及できる：

1. **レガシー設計の継承**：多くのハードウェアユーティリティのアップデータは 2000 年代に設計され、当時は HTTPS が標準ではなかった。AMD Ryzen Master のアップデータもこの系譜を引く。

2. **CDN とキャッシュのコスト問題**：HTTPS は CDN エッジでのキャッシュが HTTP より複雑で、大規模配信ではコスト増となる。ハードウェアベンダーはこのコストを回避するインセンティブを持つ。

3. **「ドライバは署名されているから安全」という誤った前提**：Windows のドライバ署名（WHQL）はドライバファイル自体の出自を検証するが、ダウンロード経路の完全性は検証しない。AMD はドライバ署名を「十分な保護」と誤認していた可能性が高い。

4. **セキュリティレビューの組織的欠如**：ハードウェア企業では、ソフトウェアアップデータは「ユーティリティ」として扱われ、コア製品（CPU/GPU ファームウェア）ほどのセキュリティレビューを受けない傾向がある。

**制度的背景：バグバウンティプログラムの機能不全**

AMD が研究者 Paul LaRosa への $10,000 報奨金支払いを拒否したことは、バグバウンティプログラムの制度的欠陥を示す：

- **報奨金支払い判斷の不透明性**：AMD は脆弱性を認識し修正したにもかかわらず、報奨金を支払わなかった。判斷基準が公開されておらず、研究者は貢獻の評価を予測できない。
- **修正までの 124 日間**：クリティカルな RCE 脆弱性の修正に 4 ヶ月を要した。業界標準（Google Project Zero の 90 日ポリシー）を超過している。
- **修正の質の不足**：修正後も CRC32 による検証のみで、暗號署名（RSA/ECDSA によるデジタル署名検証）を実裝しなかった。CRC32 は偶発的なデータ破損の検出には有効だが、意図的な改竄に対しては無力である（攻撃者は改竄後のデータに合わせて CRC32 値を再計算できる）。

## 3. この技術/政策はどのようにその問題を解決するのか?

**本來あるべき解決策：セキュアアップデータの設計原則**

AMD のアップデータが本來実裝すべきだったセキュリティ対策は以下の通り：

```
セキュアアップデータの最小要件：
  1. TLS 1.3 による通信経路の暗號化（HTTPS）
  2. 公開鍵暗號による更新パッケージのデジタル署名検証
  3. 署名検証失敗時の自動ロールバック
  4. 更新メタデータの改竄検知（The Update Framework / TUF 準拠）
```

**TUF（The Update Framework）の參照**：

TUF は CNCF の卒業プロジェクトであり、ソフトウェアアップデートシステムのセキュリティフレームワークとして以下の保護を提供する：

| TUF の保護 | 具體的メカニズム |
|-----------|----------------|
| 任意の鍵の漏洩に対する耐性 | 複數の役割鍵（root, targets, snapshot, timestamp）と閾値署名 |
| ダウングレード攻撃防止 | メタデータのバージョン番號と一貫性検証 |
| ミラーサーバー妥協への耐性 | クライアントが信頼するのは署名のみ、ミラーは信頼しない |
| 凍結攻撃（freeze attack）防止 | タイムスタンプ鍵によるメタデータの鮮度保証 |

TUF は Docker Content Trust, Fuchsia OS, PyPI（Warehouse）, Amazon Linux などで採用されている。AMD のアップデータは TUF のサブセット（少なくとも targets 鍵による署名検証と TLS 通信）を実裝するだけで、今回の脆弱性は防止できた。

**CRC32 と暗號署名の決定的な違い**：

| 特性 | CRC32 | デジタル署名（Ed25519/RSA-PSS） |
|------|-------|-------------------------------|
| 改竄検知 | 不可（攻撃者が再計算可能） | 可（秘密鍵なしでは偽造不能） |
| 衝突耐性 | 弱い（意図的な衝突生成が容易） | 強い（暗號的ハッシュ関數に依存） |
| 計算コスト | 極小 | 署名生成は中程度、検証は軽量 |
| 鍵管理 | 不要 | 秘密鍵の安全な保管が必要 |

AMD が CRC32 を選択したことは、セキュリティとパフォーマンスのトレードオフを根本的に誤解していることを示す。CRC32 は完全性「検証」ではなく完全性「チェック」であり、セキュリティ境界では使用すべきでない。

## 4. 類似の問題を解決する他の技術/フレームワーク/考え方は存在するか?

**ソフトウェアアップデートセキュリティのフレームワーク比較**：

| フレームワーク | 適用範囲 | 成熟度 | 採用例 |
|--------------|---------|--------|--------|
| TUF (The Update Framework) | 汎用アップデートシステム | CNCF Graduated | Docker, PyPI, Fuchsia |
| Uptane | 自動車 OTA アップデート | IEEE/ISTO 標準 | 自動車業界 |
| SUCS (Secure Update for Connected Systems) | IoT デバイス | 提案段階 | 研究プロジェクト |
| sigstore (cosign + rekor) | コンテナイメージ署名 | CNCF Incubating | Kubernetes エコシステム |
| Windows Update | OS レベルの更新 | プロプライエタリ | Microsoft |
| macOS Software Update | OS レベルの更新 | プロプライエタリ | Apple |

**バグバウンティプログラムのベストプラクティス比較**：

| 組織 | プログラム特性 | AMD との対比 |
|------|--------------|------------|
| Google Project Zero | 90 日間の修正期限、期限後の脆弱性公開 | AMD は 124 日を要し、期限を超過 |
| Google Vulnerability Reward Program | 報奨金額の明確なテーブル（$100〜$31,337） | AMD は報奨金判斷が不透明 |
| Microsoft Bug Bounty | シナリオベースの報奨金（RCE は最高 $250,000） | AMD は $10,000 すら支払わず |
| HackerOne プラットフォーム | 第三者仲介による透明性確保 | AMD は自社プログラムで判斷の獨立レビューなし |
| GitHub Security Bug Bounty | 修正確認後の迅速な支払い | AMD は修正後も支払い拒否 |

**業界への示唆**：

このインシデントは、ハードウェアベンダーのソフトウェアサプライチェーンセキュリティが、OS ベンダーやクラウドプロバイダと比較して著しく遅れていることを示す。特に以下の點が業界全體の課題である：

1. ハードウェア企業はソフトウェアセキュリティの専門チームを持たないことが多い
2. バグバウンティプログラムがマーケティング目的で設立され、実質的な脆弱性報告處理能力を伴わない
3. サードパーティ製ドライバ/ユーティリティのアップデータが、OS のセキュリティモデルの「盲點」となっている

規制の観點では、EU の Cyber Resilience Act（CRA）が 2027 年から施行され、ハードウェア製品に付隨するソフトウェアにもセキュリティ要件が課される。AMD のようなインシデントは、CRA の下では法令違反となりうる。
