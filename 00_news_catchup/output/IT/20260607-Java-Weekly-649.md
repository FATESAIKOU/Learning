## 1. 這個技術解決什麼問題?

Issue 649 反映 **Java 生態在 2026 上半年面對的 3 大結構性壓力**:

| 壓力 | 體現於本期文章 |
| --- | --- |
| AI 改變開發/維運 | Spring AI 2.0 M8、Tiberius LLM Security、Quarkus Skills、JFR + AI |
| 維護成本上升 | rsync mob 後開源掃描暴增 → Spring/Security in Times of AI |
| 平台碎片化 | GraalVM 25.0 升級、Quarkus 重新命名、Vert.x 雙版本、Elasticsearch 多分支 |

## 2. 這個問題為什麼會發生?(背景)

### 2.1 AI-assisted scanning 改變 OSS 維護

```text
AI security scanner 大幅提升
  └→ OSS 專案收到漏洞回報量爆增
       └→ maintainer burn-out 惡化
            └→ rsync / PyPI 事件 / Spring blog 都在談這件事
```

### 2.2 LLM 在 Java 應用層的「測試/安全」空白

傳統 Java 應用 (Spring / Quarkus / Jakarta EE) 缺乏專為 LLM prompt-injection、output validation 設計的測試框架。**Tiberius** 正是為此而生。

### 2.3 平台版本鎖定 (推測)

- GraalVM 把最低支援版本拉到 25.0 → 強迫使用者升級 native image toolchain
- Quarkus 把 Panache 改名為 Quarkus Data Hibernate → 反映 ORM 抽象層正規化
- 推測:Quarkus 團隊希望與 Hibernate ORM 對齊,避免兩套 entity 模型

### 2.4 JVM 觀測性升級

- JFR In-Process Data Redaction → 在 flight recorder 階段就過濾敏感資料
- Post-Mortem Crash Analysis with jcmd → 推測是 JEP 332 風格的延伸
- 推測:這些都是 JEP 467 / JEP 472 等新版 JEP 的實作

## 3. 這個技術是如何解決該問題的?

### 3.1 Spring/Security in Times of AI

- 議題: AI scanner 讓漏洞回報「量變」,需新的 triage 流程
- 解法: 推測為 Spring 團隊提出 maintainer 工具 (auto-triage labels, severity classifier) 以降低 burn-out

### 3.2 Hibernate 7.4 + 兩個 JSON 註解

- 議題: Java ORM 對 JSON 欄位處理冗長
- 解法: 推測 `@JsonProperty` 與某個 projection annotation 組合,讓 fetch/serialize 不再需要 DTO 層

| 註解 (推測) | 用途 |
| --- | --- |
| `@JsonView` 或 `@JsonProperty` | 序列化過濾 |
| `@Formula` 或 `@DynamicProjection` | JSON 內嵌欄位查詢 |
| 結合: 一次 SELECT + 一次序列化,跳過 conversion |  |

### 3.3 Tiberius — LLM Security Testing Framework

```text
傳統:  unit test → HTTP → controller → service
Tiberius: unit test → prompt template → LLM → assert(output schema/risk)
         └→ 專注 prompt injection, hallucination, sensitive data leak
```

| 特性 | 對照傳統工具 |
| --- | --- |
| LLM-aware assertion | OWASP LLM Top-10 |
| Java native | 推測基於 LangChain4j 或自己整合 |
| 與 JUnit 整合 | 進入 CI/CD |

### 3.4 Quarkus + AI Skills

- 把 AI migration pattern 包成「技能 (Skills)」,開發者呼叫而非從頭寫
- 對應使用者情境: Quarkus 應用遷移至 LLM 增強版本

### 3.5 GraalVM 25.0 升級

- native image 進入較新 JDK baseline
- 推測: 對應 JDK 25 LTS (推測,因 21 是 2023 LTS, 25 為 2026 預定 LTS)

### 3.6 JFR / jcmd 觀測性

| 工具 | 用途 |
| --- | --- |
| JFR In-Process Data Redaction | 錄製時遮罩 PII,符合 GDPR |
| Post-Mortem Crash Analysis with jcmd | 推測:`jcmd <pid> Thread.dump` 加上 heap analyzer |

### 3.7 WebAssembly on JVM — Endive

- 把 JVM 編譯為 WASM,在瀏覽器/邊緣裝置執行
- 推測:這是 bytecodealliance.org 的新專案,對應 WASI preview 2

## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式?

### 4.1 AI 安全測試的同類工具

| 工具 | 語言 | 對比 Tiberius |
| --- | --- | --- |
| **LangChain Eval** | Python | Python 為主,Java 整合較弱 |
| **DeepEval** | Python | LLM-as-judge 框架 |
| **Ragas** | Python | RAG 評估 |
| **Promptfoo** | Node.js / CLI | 紅隊/掃描 prompt injection |
| **Tiberius** | **Java** | 唯一在 Java 生態原生整合的 LLM 安全測試框架 |

### 4.2 JSON 處理加速的替代方案

| 方案 | 對比 Hibernate 註解 |
| --- | --- |
| **jOOQ** | SQL-first,手動控制 JSON mapping |
| **MyBatis Dynamic SQL** | XML/annotation 混合 |
| **Spring Data JPA + 客製 converter** | 推測:Tiberius 註解是這個的標準化版本 |
| **JSON-B (Jakarta JSON Binding)** | 標準化,效能仍需調校 |

### 4.3 JVM 觀測性同類工具

| 工具 | 對比 JFR + jcmd |
| --- | --- |
| **Async-Profiler** | 取樣式 profiler,與 JFR 互補 |
| **Datadog / New Relic / Dynatrace** | 商業 APM,封裝 JFR 資料 |
| **OpenTelemetry + JFR exporter** | 把 JFR 事件轉成 OTel,跨平台 |

### 4.4 思考方式

| 框架 | 啟示 |
| --- | --- |
| **AI as Code Generator vs AI as Runtime** | Java 社群目前關注「生成」多於「運行時」,Tiberius 屬少數「運行時安全」切入點 |
| **平台碎片化 vs 統一抽象** | 推測:Java 生態正朝「JEP 標準化」收斂 (如統一 In-Process 紅化 API) |
| **Open Source Sustainability** | 呼應 Armin 文 (00):AI scanner 讓 maintainer 過勞,是 Communities of Not 之所以成形的物質基礎 |

### 4.5 給 RoR + React + GCP 背景的轉換學習者
