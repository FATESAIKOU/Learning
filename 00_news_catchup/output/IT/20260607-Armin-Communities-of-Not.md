# 00. Communities of Not (原文)

**Source**: https://lucumr.pocoo.org/2026/6/6/communities-of-not/
**Author**: Armin Ronacher (Flask / Sentry / Lucumr 主理人)
**Date**: 2026/06/06
**Category**: 傳統IT技術

## 1. 這個技術解決什麼問題?

本文不是技術解法文,而是「技術社群治理」層面的反思。Armin Ronacher 點出一個**反對式社群 (Communities of Not)** 的反模式:當一群開發者以「拒絕使用 LLM」做為社群認同核心時,反而容易從批評滑向**集體獵巫 (mob behavior)**——對採用 LLM 的同行進行公審、斷章取義、羞辱,即使當事人從未自認屬於該社群。

| 問題面向 | 具體症狀 |
| --- | --- |
| 認同建構 | 把「反 X」當成唯一身分,失去對其他可能性的好奇 |
| 越界執法 | 把個人選擇解讀為「背叛」,發動想像中的驅逐 |
| 報復正當化 | 將自身對 X 的不滿,當作攻擊使用 X 者的道德許可 |
| 集體失控 | 個人羞辱升級為群體行動,傷害當事人名譽/職涯 |

## 2. 這個問題為什麼會發生?(背景)

### 觸發事件:rsync mob

2026 年 5 月,Python 維護者發起 rsync 套件 PyPI 接管請求 (squatting / takedown) 以阻擋「以 LLM 大量產生的垃圾套件」。社群把這件事延伸成對**所有**採用 LLM 工作的開發者的道德審判,甚至對 Python 維護者本身發動攻擊——Armin 認為這就是「LLM 版本的 mob」,正是觸發本文的直接原因。

### 結構性原因:否定型社群的心理動力

| 機制 | 說明 |
| --- | --- |
| 不安全感外包 | 個體對未來(職涯、語言被淘汰、技能貶值)的焦慮,透過集體否定獲得暫時安慰 |
| 部落化 (tribalism) | 「我們 vs 他們」的邊界越清楚,內部凝聚力越高,外部越容易被妖魔化 |
| 議題壟斷 | 被拒絕的事物(LLM/汽車/生育)反而佔據社群最大討論頻寬,變成隱性核心 |
| 擴音效應 | 社群媒體讓少數激烈聲音被放大,把「憤怒批評」變成「羞辱動員」 |
| 推測:開發者社群特性 | 高度理性/工具理性的自我認知,反而讓情緒性獵巫更具破壞性——「理性人」難以承認自己在霸凌 |

### 為何特別針對「LLM-skeptical developer 社群」?

- 工具變化直接威脅核心技能 (寫程式碼)
- 招募面談、code review、主管壓力都被 LLM 滲透,**迴避成本極高** (呼應 Armin 「LLM show up whether we asked or not」)
- 推測:與 Rust/MCP 等新技術相較,LLM 不是「可選學習」,而是「無聲重塑工作定義」,焦慮感更深

## 3. 這個技術是如何解決該問題的?

Armin 不是提供「技術解法」,而是提供**社群倫理框架**——把抽象呼籲化為可操作的 4 個行動:

```text
解決路徑 (Framework)
├── 1. 承認: 你在反對 X,但 X 仍然存在且影響你的工作
│      ├── 不要把「我不用 LLM」當作社群入會誓約
│      └── 接受他人嘗試 LLM 不等於背叛
├── 2. 延遲反應: 預設「最壞解讀」是認知偏誤
│      └── 反事實思考 — 對方是否真的在說你想罵的東西?
├── 3. 去升級 (de-escalate): 被激怒時主動退一步
│      └── 把攻擊能量轉成具體技術批評 (而非人身攻擊)
└── 4. 保持開放: 對新事物預設「可能有效」,而非預設「一定失敗」
       └── 這是對 in-group bias 的反向校正
```

### 套用到 rsync 事件 (推測還原)

| 該做的事 | 該避免的事 |
| --- | --- |
| 批評 PyPI 接管策略的法律/技術後果 | 羞辱發起此案的維護者 |
| 主張 LLM 套件需要 metadata 標準 | 把所有 LLM 開發者打成「投機仔」 |
| 捍衛開源治理程序的正當性 | 對採用 LLM 的 maintainer 進行驅逐動員 |

## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式?

| 替代框架 | 主張 | 對社群治理的應用 |
| --- | --- | --- |
| **Code of Conduct (Contributor Covenant / CNCF)** | 行為準則明文化 | 事前界定「不可接受的攻擊模式」,給予仲裁依據 |
| **Rust 社群治理 (RFC + teams)** | 異議走 RFC 而非社群媒體公審 | 把情緒能量導向結構化流程 |
| **Debian Social Contract** | 社群價值寫成契約,而非情緒共識 | 抵抗「今天的主流意見 = 明天的真理」 |
| **Python 本身的 PEP 13 / 流程** | 程式碼 vs 人身分開,爭議可上調解 | 推測:可借鏡處理「LLM 套件審查」爭議 |
| **推測:Charter / Bylaws 文件** | 將「社群對 X 的立場」寫成版本化文件 | 比個人情緒反覆更具可預期性 |
| **推測:Adjacent Communities (姊妹社群)** | 鼓勵跨社群交流,降低部落純度 | 讓反對者保有「也認識用 LLM 的人」的社會連結 |

### 對台灣/日本開發者社群的具體啟示

- 隨 AI 編碼工具普及,**反 LLM 社群** (e.g.「純手工寫扣」) 形成機率上升
- 管理者身分 (使用者即將轉任) 需特別注意:獵巫往往由「被背叛的資深者」發動
- 學習 Rust/MCP/GraalVM 等新技術時,若同時對 LLM 抱持懷疑,要避免把「我在學 X」當作「反 Y 社群」的入會票
