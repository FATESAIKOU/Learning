# 5. OpenAI Cuts GPT-5.6 API Prices by Up to 80%

**Category**: AI技術

## 1. 這個技術/政策解決什麼問題?

解決「先進 AI 模型基礎設施成本過高,限制 AI 應用規模化」的問題。具體痛點:

| 痛點 | 說明 |
|------|------|
| 高量 API 請求成本失控 | 處理數百萬 prompt 的平台,token 費用決定產品成敗 |
| 速度與成本無法兼得 | 延遲敏感場景需快,但快模式過去代價高 |
| 模型選擇缺乏彈性 | 單一模型難同時滿足「最大成本效益」「強推理」「低延遲」三種需求 |

OpenAI 以**降價 + 新增 Fast Mode** 應對,定位為「在每個層級提供最佳價格/智力取捨」(Sam Altman 语)。

## 2. 這個問題為什麼會發生?(背景)

### AI 競爭軸的轉移

過去一年,AI 公司競爭已從單純的 benchmark 分數,演進為多維競爭:

| 時期 | 主要競爭軸 |
|------|-----------|
| 早期 | 模型智力(benchmark、推理能力) |
| 現在 | 價格、速度、可靠性、開發者體驗、生態系 |

定價已成為產業最大戰場之一。原因:打造 AI 應用不只是選最聰明的模型,而是選**在規模下具經濟效益**的模型。

### 成本對創新的門檻效應

高 API 成本會:
- 限制新創實驗自由
- 迫使企業把 AI 功能限縮在「負擔得起」的範圍,而非「最有價值」的範圍
- 使數百萬 prompt 規模的平台,小幅降價即省下數千至數百萬美元年度成本

降價直接降低創新門檻,讓小團隊能打造過去負擔不起的複雜 AI 應用。

## 3. 這個技術/政策是如何解決該問題的?

### 3.1 GPT-5.6 系列降價明細

| 模型 | 輸入 token | 輸出 token | 降幅 | 定位 |
|------|-----------|-----------|------|------|
| **GPT-5.6 Luna** | $0.20/百萬 | $1.20/百萬 | 輸入 **−80%** | 最大成本效益、高量應用 |
| **GPT-5.6 Terra** | $2/百萬 | $12/百萬 | 輸入 **−20%** | 強推理、平衡型日常任務 |
| **GPT-5.6 Sol Fast Mode** | — | — | 速度 **2.5×**,價格 **2×** | 延遲敏感生產環境 |

### 3.2 三模型分工策略

OpenAI 提供依工作負載選模型的彈性:

| 模型 | 最佳用途 |
|------|---------|
| **Luna** | 高量應用、客戶支援聊天機器人、文件分析、工作流自動化 |
| **Terra** | 需更強推理/準確度的應用,同時壓低營運成本 |
| **Sol Fast Mode** | 語音助理、即時客服、coding copilot、互動 agent、企業自動化、金融交易助理—毫秒級延遲場景 |

### 3.3 Fast Mode 的取捨

- **效益**:回應時間提升至 2.5×,智力與標準 Sol 相同
- **代價**:價格約 2 倍
- **邏輯**:對多數企業,速度溢價值得—當毫秒計較時,更快推論顯著改善使用者體驗

### 3.4 訂閱側連動

Luna 與 Terra 的降價也反映在付費訂閱(ChatGPT Work、Codex)的用量計算—使用量現在消耗更少額度,訂閱價與配額不變。

## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式?

| 方案 | 定位 | 與 GPT-5.6 系列差異 |
|------|------|---------------------|
| **Anthropic Claude(含 Haiku 系列)** | 對手前沿模型 | 各有成本/速度取捨,競爭同樣激烈 |
| **開放權重模型(Llama、Mistral、Qwen)** | 自托管降本 | 免 API 費但需 GPU 運維,適合極高量場景 |
| **Google Gemini Flash** | 低成本前沿 | 同為「輕量快速」定位,直接競爭 Luna |
| **模型路由 / 路由器(OpenRouter 等)** | 多模型中介 | 依任務自動選最便宜達標模型 |
| **prompt 快取 / 上下文快取** | 重複 prompt 降本 | 與降價正交,可疊加節省 |

### 思考方式:依結果匹配智力(outcome-matched intelligence)

本降價背後的工程哲學:不要在每個步驟都用最強模型。一個編碼工作流可:

1. 用 **Sol** 解決不確定性、定義計畫(需強推理,少量呼叫)
2. 用 **Luna** 實作已規格化的變更、寫測試、跑測試(高量、低成本)

這是「在每階段施加最大有用智力,並為其創造的價值付對價」的取捨。降價擴大了此取捨的可行範圍。

### 對用戶情境的對照

- **Softbank AxrossRecipe 成本結構**:團隊為內部孵化新創,API 成本直接影響功能可行範圍。Luna 的 80% 降幅使原本因成本不可行的 AI 功能(如全量文件分析、背景 agent 自動化)進入可評估區間
- **即將轉管理者**:評估團隊 AI 功能 ROI 時,「Luna 高量 + Sol 關鍵步」的混合策略是現成的成本/品質平衡範本
- **Cursor+Claude 探索**:開發端 agent 的成本可控性提升,鼓勵更大膽的 agent loop 實驗(prompt-cache 重用率從 24% 提升到 90% 等案例印證)
- **Rails + GCP 團隊**:可考慮以 Luna 處理高頻分類/摘要,Terra/Sol 處理需推理的決策,在 GKE 上以 API 呼叫即可,無需自托管 GPU
