# 02. Spring AI 2.0.0-RC1 Available Now (原文)

**Source**: https://spring.io/blog/2026/06/06/spring-ai-2-0-0-RC1-available-now
**Author**: Ilayaperumal Gopinathan (Spring AI 團隊)
**Date**: 2026/06/06
**Category**: AI技術

## 1. 這個技術解決什麼問題?

Spring AI 2.0.0-RC1 解決的問題可分為三層:

1. **Tool Calling 在不同 ChatModel 之間實作不一致** — 過去 1.x 版本中,每個 ChatModel(OpenAI、Anthropic、Bedrock、Ollama…)內建自己的 tool execution loop,跨模型遷移時行為不一致,且把執行邏輯硬編進模型 client,違反職責分離。
2. **以 bean 名稱反射取得 ToolCallback 的隱式依賴** — `toolNames()` / `SpringBeanToolCallbackResolver` 透過 bean 名稱在 request time 才 resolve,造成啟動期無法靜態驗證、AOT/原生映像編譯時行為不可預期。
3. **ChatMemory + ToolCalling 的耦合導致重複注入與訊息結構損壞** — 舊設計中 ChatMemory 與 ToolCalling loop 交錯,容易把前一次 prompt 與 tool response 重複塞入下一輪,造成 LLM 看到「幻覺的對話歷史」。

次要問題:選項預設值散落在各個 ChatOptions,靜默覆蓋 provider 預設;`N()` 命名違反 Java 慣例;`ChatClient` customizer 命名不直觀;`OkHttp` 觀測性在升版後失效。

## 2. 這個問題為什麼會發生?(背景)

| 因素 | 說明 |
|---|---|
| Spring AI 1.x 演進迅速 | 1.x 期間新增 7+ 個 provider,每個 provider 各自加 tool loop,出現「複製貼上式實作」 |
| Bean 名稱反射是 Spring 慣用法 | `toolNames()` 沿用 Spring 容器「by-name 注入」的傳統,簡單但失去型別安全 |
| ChatMemory advisor 順序未深思 | 1.x 將 ChatMemory advisor 排在 ToolCalling advisor 之內,結果每次 tool-call 迭代都觸發一次 memory 注入 |
| LLM SDK 升版破壞可觀測性 | OpenAI / Anthropic Java SDK 從 `okhttp3` 改用自製 HTTP client,導致原本掛在 `OkHttp` Interceptor 的 Micrometer metrics 失效 |

> 通用背景:Spring 體系正在推動「AOT-friendly、native image 友好」的設計,任何 reflection-by-name 的 API 都被視為債。

## 3. 這個技術是如何解決該問題的?

核心策略:把「Tool Execution」從模型 client 中**拉出來**,由應用層的 `ChatClient + ToolCallingAdvisor` 統一控制。

### 3.1 統一 Tool Execution 入口

```java
// 1.x: 隱式由 ChatModel 內部跑
chatModel.call(prompt); // 內部跑 tool loop

// 2.0: 顯式由 ChatClient + Advisor 控制
ChatClient.builder(chatModel)
    .defaultAdvisors(new ToolCallingAdvisor(manager))
    .build()
    .prompt("查台北天氣")
    .tools(weatherToolCallback)        // 顯式傳入
    .call();
```

| 變更點 | 1.x 行為 | 2.0.0-RC1 行為 |
|---|---|---|
| Tool loop 執行者 | 各 ChatModel 內部 | 由應用層 `ChatClient` + `ToolCallingAdvisor` 負責 |
| Tool 註冊 | `toolNames("bean1","bean2")` 字串指定 | 顯式 `.tools(ToolCallback...)` |
| `internalToolExecutionEnabled` | 各模型開關不一 | **整個移除**(統一由 advisor 控) |
| Tool 搜尋 | 全部 context 注入 | 新增 `ToolSearchToolCallingAdvisor`(vector / Lucene / regex 三種 `ToolIndex`) |

### 3.2 ToolSearchToolCallingAdvisor — On-demand 工具發現

```text
[User Prompt] → ToolSearchAdvisor → LLM
                          ↓
        「我需要 list_files 工具」
                          ↓
   ToolIndex (vector | Lucene | regex) 搜尋匹配的 ToolCallback
                          ↓
        只把匹配到的 1~N 個工具 schema 注入 LLM context
```

效益:從「塞 200 個工具定義到 system prompt」變成「按需查找」,省 token、省成本、降低 prompt 超長導致的注意力稀釋。

### 3.3 ChatMemory 與 ToolCalling 解耦

```text
舊 (1.x):  Request → [MemoryAdvisor → ToolAdvisor(內含 memory)] → LLM
                                  ↑ 每次 tool-call 迭代都重注入 memory
新 (2.0):  Request → [MemoryAdvisor → ToolAdvisor(自管 history)] → LLM
                                  ↑ ToolAdvisor 內部管 history,memory 一次注入
```

`DEFAULT_CHAT_MEMORY_PRECEDENCE_ORDER` 被降低,使 MemoryAdvisor 包裹整個 tool loop,而不是參與每輪迭代。

### 3.4 其他穩定化措施

- **EntityParamSpec** 取代「advisor 參數夾帶 schema」的隱式做法
- **Options 預設值下放給 provider**,移除 Spring AI 靜默覆蓋
- `N()` → `n()`(Java naming convention)
- `ChatClientCustomizer` → `ChatClientBuilderCustomizer`(deprecate 舊名,新名更貼近 builder 概念)
- `OkHttp` 客製化,還原 Micrometer 可觀測性

## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式?

| 技術 | 技術解法 | 使用前提 | 使用副作用 | 預期效果 |
|---|---|---|---|---|
| **LangGraph (LangChain)** | 以 graph + node 表達 tool loop,允許自訂 routing / retry | Python 生態,需自管 state checkpoint | 框架較重,版本迭代快 breaking change 頻繁 | 對複雜 multi-agent 流程有更高表達力 |
| **Google ADK (Agent Development Kit)** | 內建 tool registry + sequential / parallel / loop agent 三種控制流 | 偏好 Google 生態,願意用 Gemini | 與 Vertex AI 綁定,跨雲受限 | 快速組合 multi-agent 應用 |
| **Spring AI 1.x 風格(bean-by-name)** | 維持既有依賴,不在 2.0 升版 | 無法承擔 migration cost | 失去 AOT/原生映像支援,debug 困難 | 短期穩定,長期技術債累積 |
| **Semantic Kernel / Kernel Memory (.NET / Python)** | Planner + Function Calling + Memory 三層分離 | 微軟生態 / .NET / Python 雙綁 | C# 為主,JS 較弱 | 與 Azure OpenAI / Microsoft Fabric 整合最佳 |

> **切入點差異**:
> - Spring AI 2.0 採「**顯式 + 集中**」(把工具控制權從各模型 client 收到 ChatClient 層)
> - LangGraph 採「**graph 化**」(把迴圈與分支用節點拓樸描述)
> - Google ADK 採「**內建模式**」(預設三種控制流,降低設計成本)
> - 1.x 風格採「**隱式反射**」(開發快、執行期才驗證)
