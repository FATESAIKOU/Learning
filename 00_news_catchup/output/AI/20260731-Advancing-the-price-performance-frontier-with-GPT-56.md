# 6. Advancing the price-performance frontier with GPT-5.6

**Source**: https://openai.com/index/advancing-the-price-performance-frontier-with-gpt-5-6
**Author**: OpenAI
**Date**: 2026-07-30
**Category**: AI技術

## 1. 這個技術/政策解決什麼問題?

解決「企業在 AI 規模化時,無法在每個工作流階段匹配到對的智力/速度/成本組合」的問題。OpenAI 以 GPT-5.6 系列**降價 + Fast Mode** 應對,目標是「讓客戶從投資 AI 的每一美元獲得更多,在時間重要時跑得更快」。

| 解決面向 | 做法 |
|---------|------|
| 高量工作成本 | Luna 降價 80%、Terra 降價 20% |
| 延遲敏感場景 | Sol 推出 Fast Mode(2.5× 速度,2× 價格,智力不變) |
| 階段化智力匹配 | 三模型分工,企業依工作流步驟選模型 |

## 2. 這個問題為什麼會發生?(背景)

### 效率 frontier 的多層來源

OpenAI 自述其效率優勢來自三層同步改進:

| 層次 | 改善內容 |
|------|---------|
| **模型本身** | GPT-5.6 採更直接的工作路徑 |
| **推論系統** | 更佳路由讓硬體維持高產能;優化生產軟體讓 token 生成更有效率 |
| **Agent 治具(harness)** | 更智慧的 context 管理避免重複已完成工作 |

三者疊加,使同量運算完成更多有用工作,降低每個結果所需的時間、token、成本。

### 自我改進的反饋迴圈

GPT-5.6 Sol 在「人類主導流程內」自主地:
- 重寫並優化生產 kernel → 端到端服務成本降 **20%**
- 設計並執行數百項實驗提升 token 生成效率 → 提升 **15%+**
- 監控訓練並在問題發生時介入

這形成更緊的反饋迴圈:**模型提升 → 更能自主工作 → 加速效率改善**。這是把模型本身用來優化自身推論堆疊的工程實踐。

### 依結果匹配智力的需求

企業使用 AI 的起點是「結果」:風險高低、錯誤成本、急迫性、規模共同決定智力/速度/可靠度/成本的正確平衡。此平衡會在同一工作流的不同步驟變化。過去模型選擇有限,企業被迫全流程用同一模型;GPT-5.6 系列擴大了選擇空間。

## 3. 這個技術/政策是如何解決該問題的?

### 3.1 定價與規格(2026-07-30 起)

| 模型 | 輸入(/百萬 token) | 輸出(/百萬 token) | 速度 | 定位 |
|------|------------------|------------------|------|------|
| **Luna** | $0.20 | $1.20 | 最快、最便宜 | 高量工作,可用工具、完成多步工作流 |
| **Terra** | $2 | $12 | 平衡 | 日常專業工作 |
| **Sol(Fast Mode)** | 不變 | 不變 | 標準的 2.5×(2× 價) | 延遲關鍵的前沿工作 |

- ChatGPT Work / Codex 訂閱價與配額不變,Terra/Luna 用量消耗更少額度
- Fast Mode 取代 Priority Processing,向後相容(`priority` 標記自動走 Fast Mode)
- AWS 同步推出

### 3.2 效能對照:相對前代與競品

| 指標 | 數據 |
|------|------|
| Luna vs 一年前前沿模型 | 相當效能,每任務約 **6 美分/美元**,速度近 **9×** |
| Luna vs Fable 5(Agents' Last Exam) | 超越對手,每任務成本低約 **99%** |
| Blitzy 實測 | prompt-cache 重用率 24%→90%,處理 2.2× 更多 context,輸出 token 減 8.5×,成本降 87%(vs GPT-5.4 mini) |
| Dust 實測 | 同 agent 任務,Luna 比前預設模型快 40%、便宜 40% |
| Notion 實測 | Terra 在個人 agent 品質相當 GPT-5.5,每任務成本減半、時間減 60% |

### 3.3 階段化工作流範例

OpenAI 給出明確的混合模型工作流:

```
編碼工作流
  ├─ [Sol]  解決不確定性、定義計畫     ← 強推理、少量呼叫
  └─ [Luna] 實作已規格化變更、寫/跑測試、評估結果  ← 高量、低成本
```

關鍵原則:**企業定義所需結果與品質標準,以評估(evals)決定何處額外智力實質改善結果、何處更快更低成本能達同品質**。

### 3.4 運算策略:規模 + 生產力雙軸

| 端點 | 策略 |
|------|------|
| 低成本端 | Luna/Terra 降價讓高量工作在更大規模經濟可行 |
| 前沿端 | Fast Mode 在回應時間重要時提供更快 Sol 存取 |

企業可把更多 AI 納入日常營運(大規模文件分析、客戶互動分類、常規實作),同時在最高關鍵性的複雜 Sol 工作負載上跑更快。收益可複合。

## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式?

| 方案 | 定位 | 與 GPT-5.6 系列差異 |
|------|------|---------------------|
| **Anthropic Claude(Haiku/Sonnet/Opus)** | 對手分層模型 | 同樣分層,但定價/速度組合不同 |
| **開放權重 + 自托管** | 極高量降本 | 免 API 費,但需 GPU 運維與推論優化工程 |
| **蒸餾 / 量化** | 把大模型壓小 | 技術可疊加,但需自有訓練流程 |
| **模型路由器(OpenRouter、自建路由)** | 依任務自動選模型 | 與階段化工作流互補,可跨廠商 |
| **evals 驅動的模型選擇** | 以評測決定匹配 | 本篇核心方法論,通用於任何模型族 |

### 思考方式:能力-成本-速度三角的階段化取捨

本篇的深層方法論:把 AI 工作流視為**多階段管線**,每階段獨立匹配智力等級。這與傳統「全流程一模型」思維根本不同:

| 舊思維 | 新思維 |
|--------|--------|
| 選一個最強模型跑全程 | 依階段風險/量級選模型 |
| 成本隨複雜度線性增長 | 高量階段用低成本模型壓制邊際成本 |
| 速度受最慢階段限制 | 關鍵瓶頸階段用 Fast Mode,其餘用標準 |

### 對用戶情境的對照

- **Softbank AxrossRecipe**:內部孵化新創對成本敏感,Luna 的價格點($0.20/$1.20)使「背景 agent 自動化」從實驗走向生產可行。建議用 evals 量化團隊既有 AI 功能的每階段品質需求,再決定 Luna/Terra/Sol 分配
- **即將轉管理者**:此「依結果匹配智力」的框架,是向團隊溝通「為何不全部用最強模型」的現成論述—成本紀律與品質維持並存
- **Cursor+Claude 探索**:開發端 agent 可套用相同階段化—Sol 規劃、Luna 實作,降低長時間 agent loop 的累積成本
- **Spring+AI 學習**:Spring AI 的 ChatClient 支援多模型注入,可實作「路由 advisor」依任務型態切換 Luna/Terra,是練手專題
- **GCP/GKE**:可在 GKE 上以 API 呼叫直接消費,無需自建推論基礎設施,降價效益直接反映在雲端帳單
