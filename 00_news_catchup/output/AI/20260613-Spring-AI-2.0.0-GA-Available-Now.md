# 01. Spring AI 2.0.0 GA Available Now

**Source**: https://spring.io/blog/2026/06/12/spring-ai-2-0-0-GA-available-now
**Author**: Christian Tzolov
**Date**: 2026-06-13
**Category**: AI技術

## 1. この技術/政策は何を解決するのか?

Spring AI 2.0.0 解決的核心問題是：**Java/Spring 生態系中缺乏一個設計一致、品質可控、可持續演進的 AI 整合框架**。

自 Spring AI 早期版本發布以來，功能、模型支援、貢獻者數量和使用者基數都快速膨脹。這種高速成長帶來了三個具體痛點：

| 痛點 | 具體表現 |
|------|----------|
| **設計不一致** | 不同模組的 API 風格、錯誤處理、序列化方式各異，開發者切換模型提供商時需重新學習 |
| **品質基準缺失** | 快速迭代導致部分模組測試覆蓋不足、null-safety 未統一、文件與實際行為脫節 |
| **可持續性風險** | 社群貢獻難以評估品質，新功能整合缺乏明確的架構約束，技術債累積速度超過償還速度 |

Spring AI 2.0.0 以「重新設定基線（setting a new baseline）」為目標，在範圍（scope）、品質（quality）、一致性（consistency）三個維度上進行全面重整，使框架能夠以可持續的方式繼續演進。

## 2. この問題が発生する背景は?

### 2.1 Java 生態系與 AI 整合的結構性落差

Python 長期主導 AI/ML 開發，其生態系（PyTorch、LangChain、LlamaIndex）已形成成熟的 AI 應用開發模式。Java 生態系在 AI 領域的整合長期處於追趕狀態：

```
Python AI 生態系成熟度:  ████████████████████░  95%
Java AI 生態系成熟度:    ██████████░░░░░░░░░░  50%
```

Spring AI 的出現填補了這一空白，但初期的高速成長模式（快速添加模型支援、功能、整合）導致了「先求有、再求好」的技術債累積。

### 2.2 Spring 生態系本身的版本演進壓力

Spring AI 2.0.0 的發布與整個 Spring 生態系的重大版本升級同步：

| 組件 | 版本 | 關鍵變更 |
|------|------|----------|
| Spring Boot | 4.0 / 4.1 | 模組化架構、AOT 編譯強化 |
| Spring Framework | 7.0 | 核心容器重構、null-safety 基礎設施 |
| Jackson | 3.x | JSON 序列化 API 大幅變更 |
| JSpecify | — | 標準化 null-safety 註解體系 |

這些上游變更既是壓力（不相容即無法使用），也是契機（可藉此重新設計內部架構）。

### 2.3 企業級 AI 整合的實際需求

從使用者（特別是 ABOUTUSER.md 中提到的 Softbank AxrossRecipe 團隊）的角度看，企業級 AI 整合需要：

- **多模型支援**：同一應用可能同時使用 OpenAI、Gemini、Claude、本地 LLM
- **可觀測性**：AI 呼叫的 latency、token 消耗、錯誤率需納入既有監控體系
- **null-safety**：生產環境中 NPE 是不可接受的故障模式
- **AOT 編譯相容性**：GraalVM native image 對 AI 應用部署成本至關重要

## 3. この技術/政策はどのようにその問題を解決するのか?

### 3.1 架構層面的重新設計

Spring AI 2.0.0 的解決方案分為四個層次：

```
┌─────────────────────────────────────────────┐
│              應用層 (User Code)               │
├─────────────────────────────────────────────┤
│  統一的 ChatClient / EmbeddingClient API     │
│  (跨模型提供商的一致介面)                      │
├─────────────────────────────────────────────┤
│  Jackson 3 + JsonHelper (標準化序列化層)      │
│  JSpecify null-safety (全程式碼庫註解)        │
├─────────────────────────────────────────────┤
│  Spring Boot 4 / Spring Framework 7          │
│  (AOT 編譯、模組化基礎設施)                    │
└─────────────────────────────────────────────┘
```

### 3.2 具體技術措施

**Jackson 3 升級與 JsonHelper**

從 Jackson 2 升級到 Jackson 3，解決了 JSON 序列化的一致性问题。新增的 `JsonHelper` 類別允許開發者提供完全自訂的 `JsonMapper`，文件中也明確說明了如何客製化預設行為。這意味著不同模型提供商（OpenAI、Gemini、Claude）的 JSON 格式差異可以在框架層統一處理，而非散落在各模組中。

**JSpecify null-safety 全覆蓋**

遵循 Spring Boot 4 的《Null-safe applications with Spring Boot 4》原則，Spring AI 程式碼庫全面使用 JSpecify 註解標記 nullability。效果：

- 編譯期靜態檢查：`@Nullable` / `@NonNull` 註解使 IDE 和編譯器能在編譯期捕捉潛在 NPE
- Kotlin 慣用語法相容：Kotlin 的 null-safety 型別系統可直接理解 JSpecify 註解，消除 Java/Kotlin 互操作的 null 問題
- 執行期防禦：結合 Spring Framework 7 的 null-safety 基礎設施，在框架邊界處自動進行 null 檢查

**Spring Boot 4 基線**

以 Spring Boot 4.0/4.1 和 Spring Framework 7.0 為最低版本要求，帶來的效益遠超「升級依賴版本」：

- AOT（Ahead-of-Time）編譯相容性：Spring AI 應用可編譯為 GraalVM native image，啟動時間從秒級降至毫秒級，對 serverless 部署和邊緣運算場景至關重要
- 模組化架構：Spring Boot 4 的模組化設計使 AI 功能可按需引入，減少不必要的依賴

### 3.3 開發者體驗改善

- **統一的 ChatClient API**：無論底層使用 OpenAI GPT-5.5、Google Gemini、Anthropic Claude 或本地 Ollama 模型，開發者面對的是同一套 API
- **文件與 Javadoc 重整**：參考文件、Javadoc、升級筆記同步更新，降低升級摩擦
- **社群貢獻品質門檻**：新的設計基準使社群 PR 的品質評估有明確標準

## 4. 類似の問題を解決する他の技術/フレームワーク/考え方は存在するか?

### 4.1 直接競爭者

| 框架 | 語言 | 策略 | 與 Spring AI 的差異 |
|------|------|------|---------------------|
| **LangChain4j** | Java | 移植 Python LangChain 設計模式 | 更接近 LangChain 的 Chain/Agent 抽象，但缺乏 Spring 深度整合 |
| **Semantic Kernel** (Microsoft) | Java/C#/Python | 微軟的 AI 編排框架 | 與 Azure/Azure AI 深度繫結，跨語言但 Java 版成熟度較低 |
| **LangChain** (Python) | Python | 事實標準的 LLM 應用框架 | 生態系最成熟，但 Java 開發者無法直接使用 |

### 4.2 設計哲學對比

Spring AI 2.0.0 的「重新設定基線」策略在開源框架演進中並非孤例：

| 案例 | 版本 | 策略 |
|------|------|------|
| **Spring Framework 6.x → 7.0** | 7.0 | 基於 Jakarta EE 9+ 和 JDK 17+ 重新設定基線，移除 deprecated API |
| **Hibernate 5.x → 6.x** | 6.0 | 全面重寫查詢引擎（SQM），統一 JPQL 和 Criteria API 的內部表示 |
| **Vue 2.x → 3.x** | 3.0 | Composition API + TypeScript 重寫，解決大型專案的設計一致性問題 |
| **React Router v5 → v6** | 6.0 | 全面重寫路由匹配演算法，統一 nested routing 的 API 設計 |

這些案例的共同模式是：**在高速成長期後，主動暫停功能擴張，集中資源進行架構重整，以換取下一階段的可持續演進能力**。

### 4.3 對企業開發者的實際意義

對於使用 Spring Boot + MyBatis 技術棧的團隊（如 ABOUTUSER.md 所述），Spring AI 2.0.0 的意義在於：

- **技術棧一致性**：AI 功能與既有 Spring 生態系（Spring Security、Spring Data、Micrometer）的整合模式一致，學習曲線平緩
- **GraalVM 相容性**：AOT 編譯支援使 AI 應用能以 native image 形式部署在資源受限的容器環境中
- **null-safety 保障**：在金融/製造業等對可靠性要求極高的領域，編譯期 null 檢查是基本需求

Spring AI 2.0.0 不是功能上的革命性跳躍，而是架構品質上的決定性升級。它為接下來 roadmap 中的新功能（更複雜的 Agent 模式、多模態處理、streaming 強化）提供了一個穩固的基礎。
