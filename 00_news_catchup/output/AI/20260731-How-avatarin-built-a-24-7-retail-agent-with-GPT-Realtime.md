# 7. How avatarin built a 24/7 retail agent with GPT-Realtime

**Source**: https://openai.com/index/avatarin
**Author**: OpenAI
**Date**: 2026-07-30
**Category**: AI技術

## 1. 這個技術/政策解決什麼問題?

解決「日本家電零售業無法在門市營業時間外提供專家級銷售支援」的問題。具體痛點:

| 痛點 | 說明 |
|------|------|
| 人力緊縮 | 經驗豐富的銷售人員難以 24/7 值勤 |
| 多語言支援 | 外國客人需求難以涵蓋 |
| 傳統聊天機器人死板 | 等關鍵字、無法理解上下文、不能引導發現需求 |

avatarin(ANA Holdings 衍生的 AI 客服公司)與 Yamada Holdings 合作,以 OpenAI GPT-Realtime 打造 **Kurashi-Marugoto AI Agent**,提供 24/7 多語音/文字購物支援。

## 2. 這個問題為什麼會發生?(背景)

### 日本零售的結構性挑戰

日本家電零售(Yamada Denki 等)的銷售品質高度依賴資深店員的商品知識—不同品類需蒐集的資訊差異極大(冰箱要看家庭人數與廚房尺寸,洗衣機要看使用頻率與空間)。這類知識難以編碼進傳統規則式聊天機器人,且店員排班無法覆蓋全天候。

### 傳統聊天機器人的限制

| 傳統機器人 | avatarin agent |
|-----------|---------------|
| 等待正確關鍵字 | 傾聽上下文 |
| 回答被動,等客人下指令 | 主動追問,引導商品發現 |
| 只能處理制式問答 | 感知客人的不確定性、變動偏好 |

CEO Akira Fukabori 點出關鍵:「客人要的不是聊天機器人,是智能。『我需要四人家庭用的冰箱,但廚房很小,該選哪台?』—真正的客服要能回答這個問題。」

### GPT-Realtime 的決定性優勢

avatarin 先前已用 OpenAI API 做語音辨識、詢問分析、員工訓練,但 Yamada Denki 專案是首次直接面對消費者。選 GPT-Realtime 的原因:單一模型同時跨越語音、文字、影像且低延遲,表現超越過往專用語音辨識系統—「與其要人適應機器規則,技術更自然地適應人類溝通方式」。

## 3. 這個技術/政策是如何解決該問題的?

### 3.1 三項核心設計

| 設計 | 做法 | 目的 |
|------|------|------|
| **資訊準確不拖慢對話** | RAG 系統將回應 grounded 在商品資訊;GPT-Realtime 維持互動流暢 | 語音對話同時取得正確商品資料 |
| **銷售專家知識轉譯為對話設計** | 把 Yamada Denki 客服知識編入對話流程與 prompting;依品類差異化資訊蒐集;guardrails 維持聚焦 | 系統在客人改需求或離題時能調適 |
| **主動問而非只答** | Agent 問後續問題挖掘實際需求 | 從問答交換走向引導式商品發現 |

### 3.2 GPT-Realtime 的多模態整合

| 模態 | 用途 |
|------|------|
| 語音 | 自然語音對話,低延遲 |
| 文字 | 多語言支援、文字輸入備援 |
| 影像 | 視覺理解(推測:商品照片辨識、畫面參照) |

單一模型跨三模態,免過去需組合多個專用系統(ASR + NLU + TTS + 視覺)的整合成本。

### 3.3 營運成果(兩週公開活動)

| 指標 | 數據 |
|------|------|
| 使用人數 | 約 30,000 |
| 服務時段 | 24/7 多語言(語音 + 文字) |
| 滿意度 | 92% 問卷正面 |
| 回饋 | 「比實際店員更好聊」「可無壓力重問」 |

### 3.4 從對話到洞察

每段對話結束附帶簡短語音問卷,回饋成為購物體驗的自然延續。最重要的發現不是規模本身,而是**每段對話揭露客人關心什麼、為何猶豫、什麼有助決策**—傳統線上購物難以看見這些洞察,AI agent 使其成為對話的一部分。

### 3.5 願景:One Intelligence. One Brand. Every interface.

avatarin 的長期藍圖:單一 AI agent 跨網頁、電話、實體門市無縫服務,同一智能攜帶客人 context 前進—一個客人、一段對話、一個品牌,無論互動發生在哪裡。「單一目的 AI 的時代結束了。」

## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式?

| 方案 | 定位 | 與本方案差異 |
|------|------|-------------|
| **Azure Cognitive Services + LLM** | 微軟多模態堆疊 | 需組合多服務,整合成本高於 GPT-Realtime 單模型 |
| **Google Dialogflow + Gemini** | 對話式 AI 平台 | 偏文字/規則,語音即時性與多模態弱 |
| **自建 ASR + LLM + TTS 管線** | 完全自控 | 延遲與整合成本高,失去 GPT-Realtime 的單模型優勢 |
| **Rasa / 開源對話框架** | 自托管對話引擎 | 規則為主,缺多模態統一推理 |
| **Spring AI + 多模型 advisor** | 用戶學習中的 JVM 路線 | 可實作 RAG + 對話設計,但即時語音需額外整合 |

### 思考方式:從問答到引導發現的介面升級

本案例體現客服介面的三階演進:

| 階段 | 行為 | 例子 |
|------|------|------|
| 1.0 關鍵字機器人 | 等關鍵字,被動答 | 「冰箱」→ 回規格表 |
| 2.0 對話式問答 | 理解問題,依文件答 | RAG 答「四人小廚房選哪台」 |
| 3.0 引導式發現 | 主動追問、挖掘需求、跨模態 | 「這台深度 60cm,您的廚房寬度?要不要看實體照片?」 |

3.0 的關鍵在於 agent 不只是「答」,而是「問」—把銷售專家的需求挖掘流程編入對話設計。

### 對用戶情境的對照

- **日本工作 + 零售相關**:avatarin 為日本 ANA 系新創、Yamada Denki 為日本最大家電零售,案例直接示範日本零售 AI 落地模式,對用戶理解日本企業 AI 採用路徑極具參考性
- **即將轉管理者**:此案例的「三項核心設計」(準確性、知識轉譯、主動性)是評估客服 AI 產品成熟度的現成檢核表
- **Spring+AI 學習**:RAG + 對話流程 + guardrails 三層皆可在 Spring AI 實作(ChatClient + Advisor + RAG),是完整的練手題材;唯即時語音需另接 GPT-Realtime API
- **Cursor+Claude 探索**:Agent「主動問而非只答」的設計理念,同樣適用開發端 agent—優秀的 coding agent 應追問需求邊界,而非只答表面指令
- **GCP/GKE**:RAG 與對話編排可部署於 GKE,語音端點呼叫 OpenAI API,架構與用戶現有基礎設施相容
