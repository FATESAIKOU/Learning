## 1. この技術/政策は何を解決するのか?

Claude Fable 5 解決的核心問題是：**如何在提供極強推理能力的同時，維持可控的安全邊界，使「最強模型」不等於「最危險模型」**。

Anthropic 將 Claude Fable 5 定位為 Claude Opus 4.5 的後繼者，在以下維度實現了跳躍式改進：

| 維度 | Opus 4.5 | Fable 5 | 改進方向 |
|------|----------|---------|----------|
| **推理能力** | 高 | 極高 | 長鏈推理、多步驟規劃、數學證明 |
| **程式碼生成** | 強 | 極強 | 大型專案級程式碼、跨檔案重構、測試生成 |
| **視覺理解** | 強 | 極強 | 複雜圖表分析、多頁文件理解、UI 截圖轉程式碼 |
| **長 context** | 200K | 推測 500K+ | 全程式碼庫分析、書籍級內容處理 |
| **安全機制** | Constitutional AI | Constitutional AI + 增強 refusal 機制 | 更精細的危害判定 |

## 2. この問題が発生する背景は?

### 2.1 前沿模型的能力-安全張力

2025-2026 年的 AI 發展呈現一個核心矛盾：

```
能力軸:
  GPT-5.5  ████████████████████████████  極強
  Fable 5  ████████████████████████████  極強
  Gemini 3 ████████████████████████████  極強

安全軸:
  GPT-5.5  ████████████                 中等（系統提示+RLHF）
  Fable 5  ██████████████████████        高（Constitutional AI + 增強 refusal）
  Gemini 3 ████████████████             中高（Google AI Principles）
```

當模型能力達到可自主編寫完整應用、分析機密文件、生成說服性政治內容的水準時，安全機制不再是「附加功能」而是「核心設計約束」。

### 2.2 Anthropic 的安全哲學演進

Anthropic 從 Claude 1 到 Fable 5 的安全策略演進路徑：

```
Claude 1 (2023):
  → Constitutional AI 初版
  → 基於書面原則的 RLHF 訓練

Claude 2 (2023):
  → 增強 harmlessness 訓練
  → 引入 system prompt 安全層

Claude 3 Opus (2024):
  → 分級安全評估（ASL-2）
  → 外部紅隊測試制度化

Claude 3.5 Sonnet (2024):
  → Computer Use 安全邊界
  → 視覺輸入的安全過濾

Claude Opus 4.5 (2025):
  → ASL-3 安全標準
  → 增強 CBRN 相關內容的 refusal

Claude Fable 5 (2026):
  → 推測 ASL-3+ 或 ASL-4 預備
  → 「guarded but over-refuses」的設計取捨
```

### 2.3 「Over-refusal」作為設計取捨

文章明確指出 Fable 5 的一個關鍵特徵：**它被守護著，可能過度拒絕（over-refuse），且仍在調整中**。

這反映了 Anthropic 的安全設計哲學：

```
安全邊界設計的兩種策略:

A. 寬鬆邊界 (OpenAI 風格):
   → 拒絕率低，使用者體驗流暢
   → 風險：可能生成有害內容
   → 修正方式：事後過濾 + 內容政策

B. 嚴格邊界 (Anthropic 風格):
   → 拒絕率高，安全邊界清晰
   → 風險：合法請求被誤拒（over-refusal）
   → 修正方式：持續調整 refusal 分類器
```

Fable 5 選擇了策略 B，並在發布後根據使用者回饋持續調整 refusal 邊界。

### 3.2 與 Opus 4.5 的關鍵差異

| 能力 | Opus 4.5 | Fable 5 | 實際影響 |
|------|----------|---------|----------|
| 長程式碼生成 | 單檔案 ~500 行 | 多檔案 ~2000+ 行 | 可一次性生成完整微服務 |
| 推理深度 | 3-5 步推理 | 10+ 步推理 | 複雜 bug 分析、架構決策 |
| 視覺精度 | 圖表基本理解 | 精確數值提取 | 可從架構圖直接生成程式碼 |
| Refusal 率 | 中等 | 較高（初期） | 安全但可能影響 UX |

### 3.3 實際使用場景

文章列舉的 Fable 5 核心使用場景：

**程式碼開發**
- 大型專案級程式碼生成（跨多檔案、含測試）
- 遺留程式碼分析與重構建議
- 架構設計文件 → 實作程式碼的端到端轉換

**研究與分析**
- 長篇技術文件的摘要與關鍵洞察提取
- 多篇論文的交叉分析與矛盾點識別
- 複雜數學/科學問題的逐步推導

**視覺任務**
- UI 設計稿 → 前端程式碼（HTML/CSS/React）
- 架構圖 → 系統設計文件
- 多頁合約/法律文件的關鍵條款提取

### 4.2 安全策略的產業分化

2026 年的 AI 安全策略呈現三條路線的分化：

```
路線 A: 「能力釋放優先，事後監管」
  代表: OpenAI (GPT-5.5), xAI (Grok-4)
  特徵: 低 refusal 率，依賴使用政策和使用者自律
  風險: 惡意使用的事前防禦較弱

路線 B: 「安全內建優先，寧嚴勿寬」
  代表: Anthropic (Claude Fable 5)
  特徵: 高 refusal 率，安全機制深度整合於模型訓練
  風險: over-refusal 影響正常使用體驗

路線 C: 「平台層安全，模型層開放」
  代表: Google (Gemini), Microsoft (Copilot)
  特徵: 模型本身較開放，安全過濾在 API/平台層實現
  風險: 安全層與模型層的分離可能產生漏洞
```

### 4.3 對開發者的實際意義

對於使用 Claude 進行 AI 驅動開發的工程師（如 ABOUTUSER.md 中提到的 Cursor + Claude 應用開發實踐），Fable 5 的意義在於：

- **程式碼生成品質跳躍**：從「函數級」提升到「專案級」，可一次性生成包含多檔案、測試、設定的完整功能模組
- **重構能力**：對遺留程式碼庫（如 ABOUTUSER.md 提到的 2000 年系統）的分析和重構建議更精確
- **Over-refusal 的實際影響**：在程式碼生成場景中，refusal 主要影響安全相關內容（如加密繞過、漏洞利用程式碼），對正常開發工作的影響有限
- **成本考量**：Fable 5 作為頂級模型，API 成本預計與 Opus 4.5 相當或更高，需在任務路由中區分「需 Fable 5 的複雜任務」和「用 Haiku 4.5 即可的簡單任務」

Claude Fable 5 代表了 Anthropic 在「最強能力」與「最嚴格安全」之間的最新平衡點。其核心命題是：**一個過度拒絕的模型可以透過回饋調整放寬，但一個過度開放的模型無法事後追加訓練階段的安全約束**。
