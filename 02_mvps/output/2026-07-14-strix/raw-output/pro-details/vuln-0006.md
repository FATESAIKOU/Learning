# Registration Validation Bypass - No Input Validation on Signup Endpoint

**ID:** vuln-0006
**Severity:** CRITICAL
**Found:** 2026-07-14 08:35:21 UTC
**Target:** https://api.axross-recipe.com/signup
**Endpoint:** /signup
**Method:** POST
**CWE:** CWE-20
**CVSS:** 9.1

## Description

The signup API endpoint at api.axross-recipe.com/signup accepts any input without validation. Duplicate email registrations silently succeed (likely overwriting existing accounts), weak passwords are accepted, password confirmation mismatches are ignored, empty usernames are allowed, invalid email formats pass through, and the terms agreement flag is not enforced. The nonce-based CSRF protection is also ineffective as the same nonce can be reused multiple times.

## Impact

An attacker can: (1) overwrite existing user accounts by registering with the same email address, effectively hijacking accounts; (2) create accounts with extremely weak passwords that are trivially guessable; (3) bypass the terms of service agreement; (4) create accounts with invalid email addresses, making attribution impossible. The account overwrite capability is particularly severe as it allows account takeover without any user interaction.

## Technical Analysis

The Ruby on Rails backend at api.axross-recipe.com/signup performs no server-side validation on user registration data. The endpoint accepts a JSON payload with user fields and a nonce, but does not validate: (1) email uniqueness - duplicate emails return success instead of an error; (2) password strength - single-character passwords are accepted; (3) password confirmation match - mismatched passwords are accepted; (4) username presence - empty usernames are accepted; (5) email format - invalid email strings are accepted; (6) terms agreement - the boolean flag is ignored. Additionally, the nonce can be reused across multiple requests, defeating its purpose as a CSRF protection mechanism.

## Proof of Concept

1. Obtain a nonce from GET /signup/nonce
2. Register an account with email "victim@example.com" and password "Password1!"
3. Register again with the same email "victim@example.com" but different password "Hacked1!"
4. Both requests return {"result":"success"} with HTTP 200
5. The second registration overwrites the first account's credentials
6. Additionally, register with password "a" - the system accepts it
7. Register with mismatched password/password_confirmation - the system accepts it
8. Register with empty username - the system accepts it
9. Register with invalid email "not-an-email" - the system accepts it
10. Register with terms_agreement: false - the system accepts it

```

HEADERS = {"Content-Type": "application/json", "Origin": "https://axross-recipe.com"}

    "username": "victim_user",
    "email": "victim@example.com",

    "password_confirmation": "OriginalPass1!",
    "terms_agreement": True,
    "nonce": nonce

# Test 3: Password mismatch
nonce4 = requests.get(f"{API}/signup/nonce", headers=HEADERS).text.strip()

# Test 5: Invalid email
nonce6 = requests.get(f"{API}/signup/nonce", headers=HEADERS).text.strip()

# Test 6: Terms not agreed

    "username": "noterms",
```

## Remediation

1. Add server-side uniqueness validation on email field - return 422 with error message when duplicate email is detected
2. Implement minimum password strength requirements (minimum 8 characters, mix of character types)
3. Validate that password and password_confirmation match before processing
4. Require non-empty username with minimum length
5. Validate email format using RFC-compliant validation
6. Enforce terms_agreement must be true before creating account
7. Implement single-use nonces - invalidate nonce after first use and reject subsequent requests with the same nonce
8. Return consistent, descriptive error messages for each validation failure
