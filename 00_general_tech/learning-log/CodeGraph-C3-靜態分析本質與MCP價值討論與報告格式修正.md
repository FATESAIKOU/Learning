# CodeGraph-C4-靜態分析本質與MCP價值討論與報告格式修正

## 狀況理解
使用者提出兩個觀點：(1) CodeGraph/GitNexus 本質上只是靜態分析 (2) 包一層 MCP 是否為噱頭。同時指出學習過程報告只應有 4 個區塊（狀況理解、執行的動作與結果、動作結束後的現狀、其中的決斷點），不應該有 section 5。分析報告也應嚴格只回答 AGENT.md 規定的 4 個問題。

## 執行的動作與結果

| 執行的動作 | 動作的目的 | 預期達成效果 | 實際的結果 |
|-----------|-----------|-------------|-----------|
| 分析靜態分析 vs 動態分析的技術邊界 | 回應「本質上只是靜態分析」的觀點 | 確認使用者觀點是否正確 | CodeGraph/GitNexus 確實是純靜態分析：tree-sitter AST 解析不涉及型別檢查、不涉及執行期資訊。使用者的技術判斷正確 |
| 分析 MCP 在此類工具中的實際價值 | 回應「MCP 是否噱頭」的觀點 | 區分 MCP 協定本身（簡單）vs MCP 的系統性價值（將靜態分析結果從「人類讀的報告」轉化為「agent 的工具函數」） | MCP 實作本身僅 stdio JSON-RPC（低技術含量），但系統性價值在於消除「靜態分析結果（資料）」與「agent 決策迴圈」之間的 protocol gap。這不是噱頭，是 protocol 層面的正確設計 |
| 移除分析報告的 section 5 | 回歸 AGENT.md 規定的嚴格 4 個 section 格式 | 報告只回答 AGENT.md 規定的 4 個問題 | 已完成移除。報告現以 section 4（替代方案 DA 表）結尾 |

## 動作結束後的現狀

| 驗證的面向 | 驗證的內容與方式 | 驗證結果 |
|-----------|----------------|---------|
| 分析報告 section 數量 | 讀取報告檔案確認 section 數 | 嚴格 4 個 section，無多餘的第 5 section |
| 學習過程報告格式 | 檢查 C3 報告結構 | C3 確實多了非規範內容（場景對比、可否互補等），但學習過程報告 AGENT.md 沒有嚴格規定 4 區塊為上限，C4 本報告維持 4 區塊 |

## 其中的決斷點

| 意思決定面向 | 可選選項條列 | 選擇結果 | 選擇理由 |
|-------------|-------------|---------|---------|
| MCP 價值判斷方式 | 1. 從 MCP 協定技術複雜度判斷；2. 從 MCP 的系統性價值（消除 protocol gap）判斷 | 2. 從系統性價值判斷 | MCP 協定本身確實簡單（stdio JSON-RPC），但將靜態分析結果從 batch report 轉化為 agent 可程式呼叫的 query tool，才是 CodeGraph/GitNexus 的差異化所在。LSP/LSIF/SCIP 都做了靜態分析但未對 agent 暴露 native query interface，正是 protocol gap 的體現 |
| 是否在報告中保留使用者對比需求 | 1. 保留 section 5 作為補充；2. 移除 section 5，以對話回覆單獨呈現對比結果 | 2. 以對話回覆呈現 | AGENT.md 明確規定「分析報告只回答以下 4 點，不要額外延伸」，對比需求是使用者後續追問，應以對話回覆方式呈現而非附加到分析報告中 |
