## 1. 這個技術解決什麼問題？

**被解決的具體問題：**

LLM 作為長期互動 agent 部署時，受限於有限的 context window，無法在跨 session、跨多輪對話中維持一致的行為與狀態追蹤。LLM agent 的無狀態特性導致以下問題：
- 忘記先前對話中約定的事項、偏好、決策
- 無法追蹤 user profile 的演變
- 多參與者、多群組、跨主題交錯的對話中，無法正確歸因資訊來源與時序
- 傳統 RAG 檢索只能抓取孤立片段，無法重構完整脈絡

EverOS 提供了從對話流中提取、結構化、鞏固並回溯長期記憶的完整作業系統，使 agent 能夠跨 session「記住、理解、持續演化」。

**文章中未明確說明的部分（推測注記）：**
- Foresight signal（前瞻信號）的具體定義在 README 中未展開，需查閱論文細節
- PersonaMem 評測的 v2 版本與 v1 的差異未說明

## 2. 這個問題為什麼會發生？（背景）

### 文章中明確提到的背景因素

| 因素 | 說明 |
|------|------|
| **LLM context window 限制** | 即使現代 LLM 支援 128K–1M token 上下文，長度仍然有限，且長上下文會稀釋注意力，降低推理精度。更重要的是，context window 是 session-bound 的，無法跨 session 延續。 |
| **現有記憶系統儲存孤立記錄** | 大多數記憶系統僅將對話轉換為獨立的向量條目存入資料庫，檢索時返回相似片段，缺乏語意鞏固與衝突解決機制。 |
| **pairwise 關係無法捕捉高階關聯** | RAG 與 graph-based 記憶系統依賴 pairwise 關係（實體間的一對一邊），無法表示 n-ary 關係（多個 episodes/facts 之間的聯合依賴），導致檢索碎片化。 |
| **多參與者協作場景缺失評測** | 現有 benchmark 多基於 dyadic（一對一）對話或單一主題，缺乏多參與者、多群組、跨主題交錯的 realistic 評測。 |

**核心矛盾：** LLM 的推理能力需要充分的上下脈絡，但給予 LLM 越長上下文，其注意力越被稀釋；反之若只給檢索片段，又缺少跨時序、跨主題的關聯脈絡。長期記憶系統需要在「上下文壓縮」與「資訊完整性」之間取得平衡。

## 3. 這個技術是如何解決該問題的？

### 核心機制：EverCore — 仿生物銘印（engram-inspired）的記憶生命週期

EverOS 的核心是 EverCore，一個自組織的長期記憶作業系統。其記憶生命週期分為三個階段：

```
                         EverCore 記憶生命週期
┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  原始對話流 (dialogue stream)                                        │
│  ┌──────────────────────────────────┐                               │
│  │ user_001: "我週末喜歡踢足球"      │                               │
│  │ user_002: "下週六有比賽要去嗎？"   │                               │
│  │ user_001: "好，但要先確認場地"     │                               │
│  └──────────────┬───────────────────┘                               │
│                 │                                                   │
│                 ▼                                                   │
│  ╔═══════════════════════════════════════════════════════════════╗  │
│  ║ Phase 1: Episodic Trace Formation                              ║  │
│  ║ ─────────────────────────────────────────────────              ║  │
│  ║ 對話流 → MemCell（記憶細胞）                                     ║  │
│  ║                                                                ║  │
│  ║ 每個 MemCell 包含：                                              ║  │
│  ║  • episode trace（情節軌跡）：連續對話的時序記錄                   ║  │
│  ║  • atomic facts（原子事實）：抽取的具體事實                        ║  │
│  ║  • Foresight signals（前瞻信號）：時間範圍內的預測性標記            ║  │
│  ║                                                                ║  │
│  ║ 實作層：src/memory_layer/memcell_extractor/                    ║  │
│  ║      → LLM-driven extraction + memory type classification       ║  │
│  ╚═══════════════════════════════════════════════════════════════╝  │
│                 │                                                   │
│                 ▼                                                   │
│  ╔═══════════════════════════════════════════════════════════════╗  │
│  ║ Phase 2: Semantic Consolidation                                ║  │
│  ║ ────────────────────────────────────────────────               ║  │
│  ║ MemCell → MemScene（記憶場景）：主題化組織                        ║  │
│  ║                                                                ║  │
│  ║  • 將語意相關的 MemCell 歸納為 Thematic MemScenes                ║  │
│  ║  • 從多個 MemCell 中蒸餾出穩定的語意結構                           ║  │
│  ║  • 更新 user profile（從會話中動態提取的用戶特徵）                  ║  │
│  ║  • 衝突解決：當新舊資訊矛盾時進行決策                              ║  │
│  ║                                                                ║  │
│  ║ 實作層：src/memory_layer/memory_extractor/                     ║  │
│  ╚═══════════════════════════════════════════════════════════════╝  │
│                 │                                                   │
│                 ▼                                                   │
│  ╔═══════════════════════════════════════════════════════════════╗  │
│  ║ Phase 3: Reconstructive Recollection                           ║  │
│  ║ ────────────────────────────────────────────────────           ║  │
│  ║ 用戶查詢 → MemScene-guided agentic retrieval                    ║  │
│  ║                                                                ║  │
│  ║  • 以 MemScene 為導引，定位相關記憶場景                           ║  │
│  ║  • hybrid retrieval: BM25 (Elasticsearch) + Vector (Milvus)    ║  │
│  ║  • RRF (Reciprocal Rank Fusion) 融合關鍵字 & 語意搜尋結果        ║  │
│  ║  • Agentic mode: LLM query expansion + multi-round retrieval    ║  │
│  ║  • 可選 reranking 提升相關性                                     ║  │
│  ║                                                                ║  │
│  ║ 實作層：src/retrieval_layer/ + src/agentic_layer/              ║  │
│  ╚═══════════════════════════════════════════════════════════════╝  │
│                 │                                                   │
│                 ▼                                                   │
│          LLM 推理（拿到必要且充分的上下文）                             │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### EverCore 六層架構

```
┌─────────────────────────────────────────┐
│  Agentic Layer (記憶操作統一介面)          │  ← 協調 extraction、vectorization、retrieval、reranking
├─────────────────────────────────────────┤
│  Memory Layer (記憶提取與管理)             │  ← MemCell extraction、memory type classification、prompts
├─────────────────────────────────────────┤
│  Retrieval Layer (多模態檢索與排序)        │  ← BM25、vector、hybrid RRF、agentic multi-round、reranking
├─────────────────────────────────────────┤
│  Business Layer (業務邏輯與 API)          │  ← FastAPI endpoints、data validation、controllers
├─────────────────────────────────────────┤
│  Infrastructure Layer (基礎設施適配器)     │  ← MongoDB、Elasticsearch、Milvus、Redis
├─────────────────────────────────────────┤
│  Core Framework (DI、生命週期、中間件)     │  ← 依賴注入容器、middleware pipeline、configuration
└─────────────────────────────────────────┘
```

### 使用 API（虛擬碼）

```python
import requests

API_BASE = "http://localhost:1995/api/v1"

# 1. 寫入記憶
add_payload = {
    "user_id": "user_001",
    "session_id": "quickstart_session",
    "messages": [
        {
            "message_id": "msg_001",
            "sender_id": "user_001",
            "sender_name": "User",
            "role": "user",
            "timestamp": 1738404000000,
            "content": "I love playing soccer on weekends",
        }
    ],
}
requests.post(f"{API_BASE}/memories", json=add_payload)

# 2. 搜尋記憶（hybrid mode）
search_payload = {
    "query": "What sports does the user like?",
    "method": "hybrid",
    "memory_types": ["episodic_memory"],
    "top_k": 5,
    "filters": {"user_id": "user_001"},
}
result = requests.post(f"{API_BASE}/memories/search", json=search_payload)
```

### 各技術的 Overengineering 臨界點

「何時不該用」與「何時該用」同等重要。以下以導入後產生的額外成本（維運、延遲、token）為基準，標示各技術在何種場景規模以下會變成 overengineering：

```
  場景規模（對話複雜度 / 輪數 / 參與者數 / 查詢推理深度）
  ◄── 低 ─────────────────────────────────────────── 高 ──►

  Mem0 ████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░  超過此線→ overengineering
  RAG  ████████████████████░░░░░░░░░░░░░░░░░░░░  超過此線→ overengineering
  Zep  ██████████████████████████████░░░░░░░░░░░  超過此線→ overengineering
  EverCore ████████████████████████████████████░  超過此線→ overengineering
  HyperMem ██████████████████████████████████████  幾乎無 overengineering 臨界
```

| 技術 | Overengineering 臨界點 | 具體判斷基準 |
|------|----------------------|-------------|
| **Mem0** | 超過「一次性問答 bot」場景 | 對話無需跨 session 記憶（例如：單次客服問答、FAQ bot）。此時 flat store 的 add+search 本身就是不必要的成本。<br>**量化閾值**：單一 user 總對話 <3 輪，或查詢僅依賴當次 context 即可回答。 |
| **RAG** | 超過「靜態知識庫搜尋」場景 | 當對話出現跨時序狀態變化（user 偏好/決策隨時間改變）、或同主題多次討論需要 consolidation 時，RAG 的 chunk-similarity 檢索會系統性返回過時資訊，產生比「無記憶」更差的幻覺。此即 overengineering：RAG 的維運成本（向量DB+embedding pipeline）仍在，但產出品質比不用記憶時更糟。<br>**量化閾值**：同 user 同主題對話 >5 輪，且 user 曾改變過立場/偏好/決定。 |
| **Zep** | 超過「無 entity 結構的對話」場景 | Zep 的核心假設是對話可被建模為 entity-relation graph。當對話以抽象討論、技術分析、想法交流為主，不存在明確的 entity（人名、組織名、產品名）時，Zep 的 graph 層會產出大量低品質或空白的 entity node，運算成本照付但無檢索增益。<br>**量化閾值**：對話中明確 entity 出現密度 <1 個/10 輪，或查詢中 entity-relation 推理需求 <20%。 |
| **EverCore** | 超過「不需要 user profile 演化」的場景 | EverCore 的核心價值在 consolidation 與 profile update。若對話量充足，但 user 特徵/偏好從不變化（例如一次性任務型 agent：每次都獨立完成一個無狀態任務），EverCore 的 4-service 基礎設施 + LLM extraction pipeline 成本遠超實際價值。consolidation 機制在 profile 為靜態時完全無效。<br>**量化閾值**：user profile 無需更新（任務為 stateless、單次完成），或 profile state 變化 <2 次/月。 |
| **HyperMem** | 幾乎無 overengineering 上限<br>（但有 underengineering 下限） | HyperMem 是方案中結構化程度最高的。其 3 層超圖 + 3 階段 LLM extraction + 8 GPU 本地 serving 的成本基線極高，但這套成本在「需要 n-ary 關聯推理」的場景中是必要成本而非 overengineering。真正的 overengineering 出現在「對話中不存在 n-ary 關聯」的場景：即所有查詢皆為 single-hop（單一事實召回），此時 hyperedge 建模的額外成本無產出。<br>**量化閾值**：對話中關聯查詢（需跨 >2 個 episodes 組合答案）比例 <10%。 |

### 各方案切入點差異

1. **EverCore vs RAG**：RAG 是檢索技術，EverCore 是記憶作業系統。RAG 的決策點是「我要搜過去對話」，EverCore 的決策點是「agent 要像人一樣記住且更新對 user 的理解」。
2. **EverCore vs HyperMem**：HyperMem 以 n-ary 超邊取勝 multi-hop 精度 (93.62%)；EverCore 以 consolidation+Foresight 取勝 profile 演化的覆蓋完整性。同專案可互補。
3. **EverCore vs Zep**：Zep 適合靜態關係推理，EverCore 適合動態狀態追蹤。
4. **EverCore vs Mem0**：Mem0 適合輕量快速整合、接受品質折損；EverCore 適合需要持續演化 user 理解、需可量化品質保證。
