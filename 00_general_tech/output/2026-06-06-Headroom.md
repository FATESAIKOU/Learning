# Headroom 技術分析報告

## 1. 這個技術解決什麼問題？

**LLM Agent 的 context window 成本過高** — AI coding agent 在執行任務時會向 LLM 發送大量 tool output（shell 執行結果、搜尋結果、API 回應、RAG chunk、log、檔案內容、對話歷史），這些內容未經壓縮直接送入模型，導致 token 使用量極大、費用高昂、且 context window 被低價值資訊佔滿。

Headroom 在這些內容到達 LLM **之前**進行內容感知壓縮（60-95% token 減省），並透過可逆壓縮機制（CCR）確保 LLM 可隨時取回原始完整資料。

## 2. 這個問題為什麼會發生？（背景）

### 文章中明確提到的原因

| 因素 | 說明 |
|------|------|
| **Agent 工作流程的特性** | AI coding agent 透過 tool calling 與環境互動，每次工具執行都產出大量原始輸出（JSON array、log、diff、檔案內容等），這些全部成為 context 的一部分 |
| **LLM 的 token-based 計費** | LLM 以輸入/輸出 token 數計費，未壓縮的冗餘內容直接轉為成本 |
| **Context window 有限** | 每個模型有 context window 上限（如 200K tokens），大量低價值內容會擠壓有用空間 |
| **Provider 原生壓縮不足** | OpenAI Compaction 只壓縮對話歷史，無法處理 JSON/tool output；且為 provider-native，無法跨 provider 使用 |
| **跨 agent 無共享記憶** | 不同 agent（Claude Code、Codex、Cursor）之間無法共享壓縮後的上下文與記憶 |

### 通用技術背景

- **Agentic AI 的興起**：2024-2025 年間 AI coding agent（Claude Code、Cursor、GitHub Copilot、Codex）大量普及，使得 agentic workflow 產生的 context 量遠超傳統 chatbot 情境
- **MCP（Model Context Protocol）** 標準化：Anthropic 推動的 MCP 協議使 tool calling 標準化，但也意味著更多結構化 tool output 需要管理
- **LLM Prompt Cache 機制**：Anthropic 的 `cache_control` 和 OpenAI 的 prefix caching 依賴 prefix 穩定性，若 system prompt 中包含動態內容（時間戳、UUID）會導致 cache miss
- **可逆壓縮（reversible compression）概念**：傳統 compress → decompress 模式要求下游能解壓，但 LLM 無法像傳統程式那樣執行解壓。因此需要「LLM 視角的可逆」—— LLM 看到壓縮版，需要時透過 tool call 取回原始版本

## 3. 這個技術是如何解決該問題的？

### 整體架構

```
 Agent / App (Claude Code, Cursor, LangChain, etc.)
        │  prompts · tool outputs · logs · RAG results · files
        ▼
 ┌─────────────────────────────────────────────────────┐
 │  Headroom  (local process, 資料不離開本地)            │
 │                                                     │
 │  CacheAligner  →  ContentRouter  →  CCR             │
 │                    ├─ SmartCrusher   (JSON 壓縮)     │
 │                    ├─ CodeCompressor (AST 壓縮)      │
 │                    ├─ LogCompressor  (log 壓縮)      │
 │                    └─ Kompress-base  (文字 ML 壓縮)  │
 │                                                     │
 │  Cross-agent memory · headroom learn · MCP           │
 └─────────────────────────────────────────────────────┘
        │  compressed prompt + retrieval tool
        ▼
 LLM Provider (Anthropic · OpenAI · Bedrock · ...)
```

### 核心機制

#### A. 三種使用模式

| 模式 | 做法 | 程式碼變化 |
|------|------|-----------|
| **Library** | `compress(messages)` 內嵌到現有應用 | 少量 |
| **Proxy** | `headroom proxy --port 8787`，改變 API base URL 即可 | 零 |
| **Agent Wrap** | `headroom wrap claude\|codex\|cursor\|aider\|copilot` | 零 |

#### B. 三階段 Pipeline

```
CacheAligner → ContentRouter → IntelligentContext
```

**Stage 1 — CacheAligner**
將 system prompt 中的動態內容（日期、UUID、session token）移至末尾，讓 prefix 保持穩定以命中 provider cache：
```
Before: "You are helpful. Current Date: 2024-12-15"  → 整段 prefix 每天 cache miss
After:  "You are helpful." [Context: Current Date: 2024-12-15]
         ↑ 穩定 cacheable prefix      ↑ 動態 tail
```

**Stage 2 — ContentRouter + 壓縮器**

自動偵測內容類型，路由到對應壓縮器：

| 內容類型 | 壓縮器 | 策略 | 典型節省 |
|----------|--------|------|----------|
| JSON dict array | SmartCrusher | 統計抽樣 + Kneedle 演算法選代表子集，保留 error/anomaly | 83-95% |
| JSON string array | SmartCrusher | Dedup + 自適應抽樣 | 60-90% |
| JSON number array | SmartCrusher | 統計摘要 + 異常值保留 | 70-85% |
| Build/test log | LogCompressor | Pattern clustering | 85-94% |
| HTML | HTMLCompressor | trafilatura-based 文章萃取 | ~95% |
| 原始碼 | CodeCompressor | tree-sitter AST (預設 passthrough) | 0-70% |
| Search 結果 | SearchCompressor | 格式壓縮 | 80-95% |
| Diff | DiffCompressor | Unified diff 壓縮 | 60-80% |
| 純文字 | TextCompressor / Kompress-base | HuggingFace ML 模型壓縮 | 60-80% |

SmartCrusher 保留策略：30% from array start (schema), 15% from end (recency), 55% by importance score (Kneedle + bigram coverage)。Error 項目永遠保留不計入 K budget。

**Stage 3 — IntelligentContext**
根據 6 維評分（recency, semantic similarity, TOIN importance, error indicators, forward references, token density）丟棄最低分訊息，使總量符合 token budget。

#### C. CCR (Compress-Cache-Retrieve) — 可逆壓縮

```
TOOL OUTPUT (1000 items)
  → SmartCrusher compress → 20 items
  → 原始內容 hash=abc123 存入本地 LRU cache
  → Marker: "[1000 items compressed to 20. Retrieve: hash=abc123]"

LLM 處理:
  Option A: LLM 用 20 items 解決 → Done (90% 節省)
  Option B: LLM calls headroom_retrieve(hash=abc123)
            → Response Handler 攔截, 從 cache 取回原始 1000 items (約 1ms)
```

#### D. Cross-Agent Memory

跨 agent 共享記憶儲存（Claude Code、Codex、Gemini），自動 dedup、agent provenance 追蹤。

#### E. headroom learn

分析失敗的 session，自動生成修正寫入 `CLAUDE.md` / `AGENTS.md` / `GEMINI.md`。

#### F. Pipeline Lifecycle

```
Setup → Pre-Start → Post-Start → Input Received → Input Cached → Input Routed
→ Input Compressed → Input Remembered → Pre-Send → Post-Send → Response Received
```

每個階段可透過 `on_pipeline_event(...)` 擴展。

#### G. 不壓縮的內容

- User message（永不壓縮）
- System prompt（內容保留，只重新排列動態部分）
- 原始碼（預設 passthrough，除非明確啟用 tree-sitter AST 壓縮）
- 短內容（< 200 tokens）
- 圖片（計為固定 token cost）
- grep/search 結果（已為緊湊格式）

## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式？

### DA 表（Decision Analysis Table）

| 技術名 | 技術解法 | 技術使用前提 | 技術使用副作用 | 技術使用預期效果 |
|--------|----------|-------------|---------------|----------------|
| **RTK** | CLI proxy，攔截 shell command 輸出並用 Rust 規則引擎過濾/壓縮（100+ 命令支援）；透過 hook 自動將 `git status` → `rtk git status` | 需安裝 Rust binary；AI agent 需支援 shell hook（Bash tool call 攔截） | 僅覆蓋 CLI command output，不處理 JSON/RAG/對話歷史/檔案內容；不可逆（無原始資料取回機制）；Windows 非 WSL 環境 hook 不可用 | 典型 30-min Claude Code session 節省 ~80% tokens，覆蓋 git/npm/cargo/docker/test/lint 等 |
| **lean-ctx** | Context OS，整合壓縮 + 記憶 + code graph + 驗證；68 個 MCP 工具；10 種 read mode；session memory 跨 chat 持久化 | 需安裝 Rust binary；需 MCP-compatible agent；適合中型以上 repo | 功能廣度大，配置選項多（68 個 MCP 工具）；單一二進位但功能涵蓋面過廣可能造成認知負擔 | 壓縮節省 60-99%（shell output）；cached re-read 僅 ~13 tokens；含 token budget dashboard |
| **OpenAI Compaction** | 僅壓縮對話歷史（conversation history），不處理 tool output | 使用 OpenAI API | Provider-locked；不處理 JSON/tool output/file content；不可逆；無法跨 agent | 僅節省對話歷史中的冗餘 |
| **Compresr / Token Co.** | 將文字發送到外部 hosted API 進行壓縮後返回 | 需網路連線；信任外部服務處理資料 | 資料傳出本地（隱私風險）；僅處理文字，不覆蓋 JSON/code/log 等結構化內容；依賴外部服務可用性 | 文字內容 token 節省 |
| **LLMLingua** | 使用小型 LM 對 prompt 做壓縮，基於 perplexity/entropy 移除低資訊 token | 需載入小型 LM 模型到本地 | 僅處理純文字 prompt，不結構化處理 JSON/code；不可逆；壓縮後可能遺失細節；額外推論 latency | 純文字 prompt 節省 50-80% tokens |

### 各方案切入點差異

```
覆蓋範圍比較:

Headroom:  ████████████████████████████████  (tool output, JSON, log, file, RAG, history, code)
RTK:       ████████████                      (CLI command output only)
lean-ctx:  ████████████████████████████████  (tool output + memory + code graph + read modes)
OpenAI C:  ████                              (conversation history only)
Compresr:  ██████                            (plain text only)
LLMLingua: ██████                            (plain text prompt only)
```

- **RTK**：從 CLI 層切入，聚焦 shell command output 的結構化過濾，最輕量但覆蓋面最窄
- **lean-ctx**：從 context 管理層切入，覆蓋面最廣（壓縮 + 記憶 + code graph + 驗證），但功能更多
- **Headroom**：從 LLM API 層切入（proxy/middleware/SDK），覆蓋所有 tool output 類型，且為可逆壓縮
