# Zed - AI 原生、GPU 加速的高效能程式碼編輯器

## 1. 這個技術解決什麼問題？

Zed 解決以下具體問題：

- **傳統程式碼編輯器運作緩慢**：基於 Electron/Chromium 技術棧的編輯器（如 VS Code、Atom）存在啟動慢、輸入延遲高、UI 反應遲鈍、記憶體佔用大等缺陷，且在大檔案（10 萬行以上）場景下效能急遽惡化。
- **缺乏真正的多核心並行能力**：JavaScript 單執行緒模型限制了編輯器對 CPU 多核心的利用率，無法將語法解析、程式碼診斷、搜尋等工作真正平行化。
- **AI 代理（Agent）整合零散且缺乏原生效能**：現有編輯器將 AI 功能外掛於既有架構上，造成 AI 代理操作與人類操作之間存在效能落差，無法即時追蹤代理的檔案變更。
- **即時協作功能缺乏編輯器底層的原生支援**：傳統協作方案透過外掛實現，無法達到字元級別的一致性與低延遲即時同步。

## 2. 這個問題為什麼會發生？（背景）

### 文章中明確提到的背景

- Atom（Zed 創始團隊的前作）是基於 Electron (Chromium fork) 建構的，團隊在 2017 年左右體認到 Electron/JavaScript 技術棧已成為效能上限。
- JavaScript 中陣列實際是指標陣列，無法控制記憶體佈局；垃圾回收（GC）暫停無法控制；DOM 協商渲染路徑冗長。
- 在 Electron 架構下，要將某子系統遷移到背景執行緒以實現平行化，必須先用 C++ 重寫該子系統、建立 JS 綁定、保持 JS 風格的 API，開發成本極高（文中 Max 的描述）。
- Nathan Sobo 在 2017 年的日記中寫下「我們必須從頭開始」（we have to start over）。

### 通用技術背景

- **Electron 架構的本質限制**：Electron 本質上是一個完整的 Chromium 瀏覽器實例，每個視窗都是一個渲染進程。對程式碼編輯器而言，Electron 的 DOM 渲染路徑是主要的效能瓶頸：DOM 樹操作、樣式計算、佈局重排（reflow）、合成（compositing）等步驟全部在 CPU 上執行，無法直接利用 GPU 的平行運算能力。
- **JavaScript 語言的記憶體模型限制**：JS 缺乏對記憶體佈局的精細控制、沒有真正的多執行緒共享記憶體模型（SharedArrayBuffer 能力有限）、缺乏零成本抽象（zero-cost abstraction）。
- **傳統文字表示資料結構的限制**：多數編輯器使用字串（string）、gap buffer 或 piece table 來表示文字內容，這些結構在並行存取場景下有不同程度的限制（gap buffer 不支援多執行緒快照，piece table 的查詢效率受限）。

## 3. 這個技術是如何解決該問題的？

### 核心機制：從底層重新建構整個編輯器技術棧

#### 3.1 全 Rust 實作

```
// Zed 的技術棧層級
┌─────────────────────────────────────────┐
│  Editor Layer（多緩衝區、語法折疊等）     │
├─────────────────────────────────────────┤
│  GPUI（自研 GPU 加速 UI 框架）           │
├─────────────────────────────────────────┤
│  SumTree（通用 B+ 樹，支援快照/並行）     │
├─────────────────────────────────────────┤
│  Rope（基於 SumTree 的文字表示）          │
├─────────────────────────────────────────┤
│  Platform Graphics API (Metal/DX/Vulkan)  │
└─────────────────────────────────────────┘
```

- 整個編輯器以 Rust 實作（GitHub 上 97.8% 為 Rust 程式碼），利用 Rust 的所有權系統、`Arc`（原子參考計數）、零成本抽象實現零開銷的並行存取，消除 GC 暫停。
- 編譯器層級的嚴格檢查使得團隊能以高信心合併社群貢獻的程式碼。

#### 3.2 GPUI：GPU 加速的 UI 框架

```
// 概念模型：Zed 將 UI 渲染視為著色器（shader）問題
// 而非 DOM 操作問題
//
// 傳統 Electron: JS → DOM 樹 → 樣式計算 → 佈局 → 合成 → 像素
// GPUI:         Rust → 元素樹 → 批次 GPU 繪製指令 → Shader → 像素
//
// 每個影格 (frame) 的目標時間 < 3ms
```

- GPUI 是 Zed 團隊自研的 GPU 加速 UI 框架，類似於「用寫遊戲引擎的方式寫編輯器」。
- 直接使用平台圖形 API (macOS: Metal, 其他: DirectX / Vulkan) 進行渲染。
- 使用簽署距離場（signed distance fields）等技術渲染文字。
- 目標維持 120 FPS 渲染。

#### 3.3 SumTree 與 Rope：並行友善的文字資料結構

```
// Rope 的類型定義（簡化）
struct Rope {
    chunks: SumTree<Chunk>,  // SumTree 而非傳統二元樹繩索
}

struct Chunk(ArrayString<{ 2 * CHUNK_BASE }>);
// CHUNK_BASE = 64（release 模式）

// TextSummary：每個節點的摘要
struct TextSummary {
    len: usize,              // UTF-8 長度
    len_utf16: OffsetUtf16,  // UTF-16 長度（LSP 相容）
    lines: Point,            // 行數與最後一行位置
    first_line_chars: u32,   // 首行字元數
    last_line_chars: u32,    // 尾行字元數
    last_line_len_utf16: u32,
    longest_row: u32,        // 最長行的索引
    longest_row_chars: u32,  // 最長行的字元數
}
```

SumTree 的關鍵特性：

- **B+ 樹結構**：每個內部節點包含其子樹的摘要總和（Sum of Summaries），支援 O(log N) 的索引查找。
- **並行快照**：透過 `Arc` 參考計數，可以 O(1) 時間產生整個文字的唯讀快照，傳遞給背景執行緒進行 Tree-sitter 解析或其他處理，無需複製文字內容。
- **多維度索引**：可以在 O(log N) 時間內沿任意維度（如位元組偏移量、行號、UTF-16 偏移量）進行查找，並同時聚合其他維度的資訊。

```rust
// SumTree 的 cursor 機制：沿一個維度搜尋，同時聚合多個維度
let mut cursor = self.chunks.cursor::<(usize, Point)>();
cursor.seek(&offset, Bias::Left, &());
// cursor.start().0 = 偏移量, cursor.start().1 = 行/列座標
```

- SumTree 不僅用於文字表示，也用在專案檔案列表、Git blame 資訊、對話訊息、診斷資訊等 20+ 處。

#### 3.4 CRDT 協作引擎與 DeltaDB

- 使用無衝突複製資料型別（CRDT）實現多人即時協作，支援字元級別的一致性編輯。
- 開發中的 DeltaDB 是基於 CRDT 的同步引擎，能讓多個人類和 AI 代理共享單一一致的程式碼庫視圖。

#### 3.5 AI 原生整合

```
Agent Panel → 使用者描述任務 → Agent 自動探索上下文、編輯檔案、執行工具
              → 使用者即時追蹤 Agent 操作（與人類協作相同的多人基礎設施）
              → 可編輯的 unified diff 供審查 → 接受或拒絕所有變更
```

- **Agentic Editing**：內建 AI 代理面板，代理可以編輯檔案、導航程式碼、執行工具。
- **Parallel Agents**：同時執行多個代理執行緒，跨多個專案並行工作。
- **Edit Prediction (Zeta2)**：開源權重的編輯預測模型，在按鍵粒度預測下一個編輯，支援 Tab 連續接受多個後續編輯。
- **ACP (Agent Client Protocol)**：開放的代理通訊協定，支援 Claude Agent、Codex、OpenCode、Gemini CLI、Cursor 等外部代理接入。
- **MCP (Model Context Protocol)**：支援連接 MCP 伺服器擴展代理的知識範圍。
- **多種模型選擇**：Zed 託管（Claude Opus、GPT 5.4）、自備 API Key、Ollama 本地模型、ChatGPT 訂閱帳號。

#### 3.6 開放生態

- 開源（GPL-3.0 + Apache-2.0）
- WASM 擴展系統（基於 Tree-sitter）
- ACP 開放協定
- Zeta2 開放權重模型

## 4. 是否存在解決類似問題的其他技術 / 框架 / 思考方式？

### DA（Decision Analysis）表

| 技術名 | 技術解法 | 技術使用前提 | 技術使用副作用 | 技術使用預期效果 |
|--------|----------|-------------|---------------|-----------------|
| **VS Code** | Electron 框架 + TypeScript + 外掛架構；透過擴展（Extension）整合 AI（GitHub Copilot、Copilot Chat）和 LSP | 接受 Electron 的效能開銷；依賴擴展生態系統獲得功能 | 記憶體佔用大（1-2GB 常見）；輸入延遲 20-50ms；GC 暫停不可控；AI 功能為擴展層級整合，非原生 | 功能覆蓋面最廣（4 萬+ 擴展）；社群資源最豐富；跨平台一致 |
| **Cursor** | 基於 VS Code (Electron) fork，在核心層級深度整合 AI（內建 Agent、Composer、Tab 補全），非外掛形式 | 接受 Electron 效能天花板；依賴 VS Code 擴展生態；需訂閱 Cursor Pro | 與 VS Code 擴展生態相容但不能同時使用 VS Code 官方版本；AI 功能深度整合但底層仍是 Electron | AI 原生體驗（深於 VS Code + Copilot）；學習曲線低（來自 VS Code 的遷移者） |
| **IntelliJ IDEA** | JVM 原生（Swing/自研 UI）+ 靜態分析引擎；內建重構、程式碼檢查、框架支援；透過外掛整合 AI（JetBrains AI Assistant） | 接受 JVM 的記憶體開銷（建議配置 4GB+）；接受較長的啟動時間（10-30 秒）；需要 JetBrains 生態授權 | 記憶體佔用極大（2-4GB 常見）；啟動慢；UI 不如原生輕量；AI 功能為後期疊加 | 靜態分析能力最強（跨檔案重構、型別推導、依賴分析）；針對特定語言的深度支援（Java/Kotlin/Android 等） |
| **Neovim** | C 語言核心 + Lua 擴展；終端機內執行；透過 Lua 外掛整合 LSP、DAP、AI（如 avante.nvim、CopilotChat.nvim） | 接受終端機環境的限制（字型渲染、滑鼠互動）；需要自行配置外掛組合；學習曲線較高 | 圖形功能受限（無 GPU 渲染、無富文字）；配置複雜度高（需自行組合外掛生態）；多執行緒支援有限 | 極低記憶體佔用（<100MB）；鍵盤驅動操作效率極高；高度可自訂 |

### 各技術解決問題的切入點差異

1. **Zed**：從底層資料結構和 GPU 渲染開始，重新設計整個編輯器架構，以獲得原生層級的效能，並將 AI 代理操作與人類操作統一在同一多人基礎設施上。切入點是「效能極限 + AI 原生」。

2. **VS Code**：以 Web 技術實現跨平台一致性，透過龐大的擴展生態系統涵蓋各種開發場景。切入點是「功能覆蓋廣度 + 生態系統」。

3. **Cursor**：在 VS Code 基礎上，將 AI 從外掛層級提升為核心功能，提供原生層級的 AI 代理體驗。切入點是「AI 體驗深度 + VS Code 相容性」。

4. **IntelliJ IDEA**：透過自有的靜態分析引擎和語言模型實現最深度的程式碼理解與重構能力。切入點是「程式碼語意理解深度 + 語言特定工具鏈」。

5. **Neovim**：以最小資源佔用和鍵盤驅動操作實現最高效率的編輯流程。切入點是「資源效率 + 可自訂性」。
